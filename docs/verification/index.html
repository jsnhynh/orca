Verification¶

  • All 67 official RISC-V architecture tests (RV32IMA, Zicsr, Zifencei) pass in simulation and on the KV260.

  • Each test retires exactly the same number of instructions on the board as in simulation.

  • CoreMark and a no-MMU Linux boot pass a reference model check on every retired instruction.

  • 100 random programs per run match Sail, the official RISC-V model.

  • 8 of 8 Linux boots on the board finished a scripted shell session.

  • Line coverage of ORCA’s RTL is 100%.

I verified bottom up: every block on its own first, then each layer above runs bigger programs against a stronger reference. When something broke late, I pushed it back down by giving the block bench that should have caught it a directed test.

1. Block Testbenches¶

50 testbenches, from the ALU up to the AXI crossbar. 46 run under Verilator with make regress, coremark_tb and linux_boot_tb have their own targets, and two run in Vivado’s simulator because they need the real XPM memory models.

Most benches compare the block against a simple reference model every cycle: a queue’s model is a SystemVerilog queue, a predictor table’s is an array indexed the same way. Directed cases hit specific corners (like a flush in the same cycle as a write), and long constrained-random runs cover the combinations. sim/common/ has the shared checker, an assertion macro and a functional coverage helper whose named scenarios all have to be hit.

Why shadow references during rewrites. A lot of blocks got rewritten late for timing or area. During each rewrite the bench kept the old block next to the new one with an assertion that their outputs matched every cycle, and CoreMark’s cycle count had to stay the same. Once the new block passed every layer the old copy came out, so the benches check the block’s contract, not an old implementation.

Branch outcomes count every term of every condition, which is why that rate is lower. A line no test can reach gets // cov-off: <reason> on the line itself, but I’d rather delete dead code than waive it, and most unreachable branches ended up deleted and replaced with an assertion. The gate compares hit counts per file against a recorded baseline and fails on any lost hit, so adding a feature never breaks it but losing a test always does.

3. Architecture Tests¶

The 67 official tests cover RV32I, M, Zaamo, Zalrsc, Zicsr, Zifencei, ExceptionsSm and InterruptsSm. Each checks itself against values Sail computed when the test was built and writes pass or fail into the last word of the DMA region.

Every test is one flat image at 0x1000_0000, and the same file runs in Verilator and on the board through the same boot stub. Each also stores its cycle and retired counts below the result, so ./orca act-compare can check the board against simulation: retired instructions match on all 67, and board cycles are 1.17 to 2.31 times simulation (median 1.87) since the board’s DDR is slower than the model. With --quick, all 67 run on the board in about 30 seconds.

4. Random Programs vs Sail¶

A generator writes seeded RV32IMA programs mixing arithmetic, multiply and divide, loads and stores, atomics, CSRs, branches, counted loops and deliberate traps. They stay checkable by design: accesses stay aligned in a 256-byte scratch area, branches only go forward except counted loops, and nothing reads a counter. Most instructions use a small set of registers to stress forwarding and wakeup. A trap handler logs each trap and skips the instruction.

Each program dumps its registers, scratch area and trap log into a signature, and Sail’s signature has to match. The pre-commit tier runs 100 programs, and the last nightly ran 600. For a failing seed, diverge.py walks the RTL’s and Sail’s register writes side by side to the first difference, and reduce.py cuts the program down from a few hundred instructions to a few dozen.

5. CoreMark and Embench Setup¶

For the comparison, every core runs the same CoreMark and Embench-IoT sources built with GCC 15.2 at -O3, each in its own simulator. CoreMark runs 10 iterations from a cold start, so cache warm-up counts the same for everyone, and a shared Embench support file reads mcycle and minstret right around each timed call.

On the board, CoreMark runs 12,000 iterations from DDR and prints ORCA’s cycle and instruction counters around the timed loop, so the score is iterations over cycles times the clock. Embench runs each of the 19 programs once and writes its cycles and instructions into the DMA region, and the score is the geometric mean of speed against Embench’s reference.

6. Linux Boot¶

The retirement oracle is an RV32IMA model in SystemVerilog that steps next to the core. Every cycle it checks the next PC, destination register and written value of whatever retired. It only reads retired state and keeps its own copy of DDR, so it shares nothing with the speculative core or the caches. For values it can’t predict (device registers, uncached loads, CSR reads, SC.W success) it takes the core’s value. The first mismatch stops the run and prints the last 48 retirements, so a bad value gets caught at the instruction that made it, not millions of cycles later.

linux_boot_tb boots to login: under the oracle, and on the earlier RTL also with a DDR model that stalls 40% of handshakes and adds up to 100 cycles of latency (735,011,508 cycles).

That stalled boot found the one bug that changed the microarchitecture. The L1 predictor skipped its check of an L0 prediction when the next packet’s address wasn’t known yet, so fetch could follow a path nothing later would correct, and on the board that showed up as boots dying partway. The check now covers every response (branch prediction).
