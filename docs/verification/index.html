Verification¶

  • All 67 official RISC-V architecture tests (RV32IMA, Zicsr, Zifencei) pass in simulation and on the KV260.

  • Each of those tests retires the same number of instructions on the board as in simulation.

  • CoreMark and a no-MMU Linux boot pass a reference model check on every retired instruction.

  • 100 random programs per run match Sail, the official RISC-V model.

  • 40 of 40 Linux boots on the board completed a scripted shell session.

  • Line coverage of ORCA’s RTL is 100%. Each line no test can reach carries a waiver comment with its reason.

Verification was done bottom up. Each block was verified on its own before system-level testing, and each later layer runs larger programs with a stronger reference. A failure found late is pushed back down: the block bench that should have caught it receives a directed test.

1. Block Testbenches¶

50 testbenches cover the design, from the ALU up to the AXI crossbar. 46 run under Verilator with make regress, the two long-program benches (coremark_tb, linux_boot_tb) have their own targets, and two run in Vivado’s simulator because they need the native XPM memory models.

Most benches compare the RTL against a reference model of the block every cycle. The model is written separately from the RTL and kept simple: a queue’s model is a SystemVerilog queue, and a predictor table’s model is an array indexed the same way. Directed cases cover specific corners, such as a flush in the same cycle as a write, and long constrained random runs cover the combinations. Shared helpers in sim/common/ provide a checker class that fails the run on any failed check, an assertion macro for per-cycle invariants, and a functional coverage helper whose named scenarios must each be hit.

Design Decision: Shadow References During Rewrites¶

Many blocks were rewritten for timing or area late in the project. During each rewrite, the bench kept the old block beside the new one with an assertion that their outputs matched every cycle, and CoreMark’s cycle count had to stay identical. The old copy was removed once the new block passed every layer, so the shipped benches check the block’s contract and not an older implementation.

Branch outcomes count every term of every condition, which is why that rate sits below line coverage. The functional scenarios cover the AXI interconnect, cache replacement and the cache inside the SoC.

A line no test can reach carries // cov-off: <reason> on the line itself, so the waiver moves with the code. When a whole branch turned out to be unreachable, it was deleted and replaced with an assertion. The coverage gate compares per-file hit counts against a recorded baseline and fails on any lost hit, while new uncovered code passes, so adding a feature never breaks the gate.

3. Architecture Tests¶

The 67 official tests cover RV32I, M, Zaamo, Zalrsc, Zicsr, Zifencei, ExceptionsSm and InterruptsSm. Each test checks itself against values Sail computed when the test was built, and writes a pass or fail word to the mailbox, the last word of the DMA region.

Each test is linked as a single flat image at 0x1000_0000, and the same file runs in Verilator and on the board through the same boot stub. Each test also stores its cycle and retired instruction counts just below the mailbox. ./orca act-compare then checks the board against simulation: retired instructions match on all 67 tests, and board cycles run 1.18 to 2.30 times the simulation (median 1.87), since the board’s DDR has higher latency than the model.

On the board, each test normally starts from a fresh bitstream, which takes about seven seconds per test. The --quick option loads the bitstream once and restarts ORCA between tests, completing all 67 in about 30 seconds.

4. Random Programs vs Sail¶

A generator writes seeded RV32IMA programs from arithmetic, multiply and divide, loads and stores, atomics, CSR accesses, branches, counted loops and deliberate traps (ECALL, EBREAK, an illegal word, misaligned accesses). The programs are constrained to stay checkable: (1) accesses stay aligned inside a 256-byte scratch region, (2) branches only go forward except for counted loops, and (3) no instruction reads a counter or timer. Most instructions draw from a small set of registers to exercise the bypass and wakeup paths. A machine-mode handler logs each trap’s cause, PC and value, then skips the instruction.

Each program ends by dumping its registers, scratch region and trap log into a signature area. Sail runs the same program, and the two signatures must match. The pre-commit tier runs 100 programs, and the final nightly run used 600.

For a failing seed, diverge.py walks the RTL’s and Sail’s register writes side by side and stops at the first difference. reduce.py then deletes chunks of the program for as long as the failure persists, shrinking a few hundred instructions down to a few dozen.

5. CoreMark and Embench Setup¶

In simulation, coremark_tb runs CoreMark with the retirement oracle described below, and the run must also print CoreMark’s correct checksums.

For the comparison with other cores, every core runs the same CoreMark and Embench-IoT sources built with GCC 15.2 at -O3, each in its own simulator. CoreMark runs 10 iterations from a cold start, so cache warm-up counts equally for every core. A shared Embench support file reads mcycle and minstret immediately around each timed call and reports through each core’s own output mechanism.

On the board, CoreMark runs 12,000 iterations from DDR and prints ORCA’s cycle and instruction counters around the timed loop; the score is iterations over cycles times the clock. Embench runs each of the 19 programs once and writes the return code, cycles and instructions of the timed call into the DMA region; the score is the geometric mean of speed against Embench’s reference numbers.

6. Linux Boot¶

The retirement oracle is an RV32IMA model written in SystemVerilog that steps alongside the core. Each cycle it reads what retired and checks the next PC, the destination register and the written value. It reads only retired state and keeps its own copy of DDR, so it shares no logic with the speculative core or the caches. Some values cannot be predicted (device registers, uncached loads, CSR reads, SC.W success), so for those the oracle takes the core’s value, and it resynchronizes its PC on traps and MRET. The first mismatch stops the run and prints the last 48 retirements, which catches a wrong value at the instruction that produced it rather than millions of cycles later.

linux_boot_tb boots the kernel to login: under the oracle, and again with a DDR model that stalls 40% of handshakes and adds up to 100 cycles of latency. The stalled boot reached login: in 735,011,508 cycles and 99,878,400 retirements.

The stalled-memory boot exposed the one bug that changed the microarchitecture. The L1 predictor skipped its check of an L0 prediction when the next packet’s address was still unknown, which let fetch follow a path that no later stage would correct. On the board, this appeared as boots that failed partway through. The check now covers every response (branch prediction), and the board then completed 40 of 40 boots.
