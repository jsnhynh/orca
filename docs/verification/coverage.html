Coverage¶

I track three kinds of evidence separately, because each answers a different question.

  1. Assertions check invariants every cycle and stay enabled in all runs. A pass means none fired.

  2. Functional coverage records the scenarios the tests are meant to reach, such as a stall, an error response or a cache writeback. A required scenario that is never reached fails the run.

  3. Code coverage shows which lines and branches the tests executed. It locates missing tests and says nothing about correctness on its own.

Current numbers¶

The full coverage run is the regression, the directed program tests, the 67 architecture tests and CoreMark, all under instrumentation. It executes every one of the 5,565 counted lines of ORCA’s own RTL and 64,547 of 81,177 branch outcomes (79.5%). Vendored and generated code is counted separately.

Two kinds of lines are left out, and each is listed with its reason. Verilator puts a line’s counter after a return, so a function arm that returns can never show a hit. A line no test can reach carries a cov-off comment with its reason on the line itself, so the waiver moves with the code: the unused encodings of a state machine, a default arm for a selector that is fully listed, and cases the decoder rejects before the unit sees them. Where the unreachable code was a whole branch, I deleted it and put an assertion in its place instead of waiving it. No line is left open: the last ones were a rename-to-dispatch slot compaction the front end can never trigger, which I deleted, and a load/store unit recovery guard that can never fire, which carries an assertion that checks it in every simulation.

Functional coverage has 15 named scenarios across three benches: the AXI interconnect, cache replacement and the cache with the SoC. All 15 are reached.

Interpreting the numbers¶

The numbers are a map. A line that is never executed is either missing a test or unreachable, and I review each one. A gate compares hit counts with the last recorded run per file: a lost hit fails it, and new code that is not yet tested does not. Line coverage says little about branch outcomes, which are lower, and the scenario matrix still has gaps, for example the clock-crossing FIFOs under full and reset conditions. Those gaps are tracked and are not counted as covered.

Running it¶

make coverage runs the regression with line and expression coverage and writes a merged report with a ranked list of the files that have the most uncovered code. Adding COVERAGE_PROGRAMS=1 COVERAGE_ACT=1 COVERAGE_COREMARK=1 includes the program tests, the architecture tests and CoreMark. make functional-coverage runs the five scenario benches.

I run verification in four tiers. The smoke tier takes seconds (lint, documentation checks, the helper tests and one program). The pre-change tier adds the regression, the FPGA-shaped smoke test, the program tests, the host-driven SoC tests and 100 random programs against Sail. The full tier, which ./orca gate runs on a frozen copy of the tree, adds the CoreMark retirement oracle and the architecture tests without coverage. The nightly tier runs everything under coverage, then the CoreMark retirement oracle, the architecture tests and the coverage gate. Each run keeps a log per step and one result file, and a skipped step is reported as skipped, never as passed.
