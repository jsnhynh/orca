Design Decisions¶

The microarchitecture pages describe what the core does. This page keeps the measurements behind some of the choices, including the options I measured and did not take. Each table compares variants of the same RTL, built and run the same way, so the numbers within a table are comparable with each other.

Embench scores are Embench-IoT’s speed score per MHz (higher is better). CoreMark is timed cycles for the same run (lower is better). LUT counts are the core plus its L1 caches, synthesized out of context for the KV260 part.

How a branch mispredict is recovered¶

When execute finds that a branch was mispredicted, everything fetched after it is wrong. The question is how much of the pipeline to repair right away and how much to leave until the branch retires.

The usual answer is checkpoints. Rename saves a copy of its map for each in-flight branch. Every instruction carries a mask of the branches it is younger than, and a mispredict throws away exactly the work with that branch’s bit. The correct path can rename the very next cycle. The cost is that the mask travels with every instruction, and every queue and functional unit needs logic to squash by it.

I measured how many checkpoint slots pay for themselves. A branch that finds no free slot is repaired at commit, with a full flush and refetch.

Two slots cost as much area as four, because the snapshots live in LUT RAM whose cost follows width, not depth. What does scale with the slot count is the masks everywhere else. Zero slots saves about 2,500 LUTs and loses 2.3% on Embench, because a mispredict now waits for its branch to reach the head before anything restarts.

Then I tried a middle path with no checkpoints at all. On a mispredict, execute redirects only the front end: fetch restarts on the correct path, and the FTQ, global history and return stack roll back. The back end is left alone. Rename simply stops taking new instructions until the branch retires, and then the whole back end is flushed and rename restores its committed map. This is safe because rename hands out work in program order: everything already in the back end is older than anything on the correct path, so nothing needs to be picked apart.

The front-end redirect gets almost all of the checkpoint performance back. While the back end drains the older work, the front end is already fetching, predicting and decoding the correct path, so by the time the flush comes the instruction buffer is full. It is within 0.3% of four slots on Embench and 0.06% on CoreMark, with about 1,500 fewer LUTs and no masks anywhere in the back end. I chose it.

The first version of the redirect was much slower: CoreMark took 11% more cycles, and one Embench program ran 40% longer. A loop branch was being redirected again on every iteration, about 50,000 times against roughly 500 real mispredicts, so the predictor never learned it. When a branch retired in the same cycle a redirect cut the FTQ back, the FTQ dropped that retirement, so from then on commit no longer lined up with its FTQ entries and the branch was never trained. Once the FTQ applied both in that cycle, redirects fell to the real mispredict count.

At -O3, the front-end redirect design scores 2.277 Embench per MHz. NaxRiscv, built with the same compiler and flags, scores 2.266.

A NaxRiscv-style issue window¶

Reaching 175 MHz¶

At 175 MHz (a 5.714 ns clock), the core missed timing by about 0.46 ns, and not on one path. Six unrelated paths each missed by about the same amount, so fixing one only exposed the next. Most of the delay was routing, not logic.

I changed the tools first. The same RTL with a different placement and routing directive (ExtraNetDelay_high placement, AggressiveExplore routing) gained about 0.2 ns. Turning on retiming in synthesis lost 0.1 ns.

Then I shortened the paths. Almost every fix had the same shape: something late (a grant, a ready, a commit decision) sat in front of a lot of work, and I moved the work ahead of it. Instead of picking a value and then comparing it, the logic compares every candidate in parallel and lets the late signal pick a result at the end. None of these changes moves an instruction by a single cycle. I checked that cycle for cycle on CoreMark and four Embench programs, and most of them carry a simulation check that compares the new logic with the old form every cycle.

The last and largest one was the scheduler’s wakeup. A result reaches the two result-bus lanes through a mux controlled by the bus grant, and every scheduler entry compared its operand tags against those lanes. So the path ran grant, mux, compare, ready, select, all in one cycle. Now every entry compares against all six execution units’ results directly, and the grant only qualifies the matches. That costs about 230 LUTs in the scheduler and closed the last gap. Doing the same for the uncached load at the head of the load queue cost about 460 more in the load/store queue.

One move did change timing. When a branch mispredict is only caught at commit, the history restore in the branch predictor now happens one cycle after the branch retires instead of in the same cycle. It made no difference to the cycle count of any program I ran, because the front end is restarting from the flush in that cycle anyway.

The +0.009 ns comes from one set of directives on this exact RTL. Small RTL changes moved the result by about 0.2 ns in either direction, and other placement directives on the same RTL still fail, so 175 MHz closes but without much margin.

On the board¶

The numbers above are for the core on its own. On the KV260 the core sits inside the full design (the processor system’s ports, the memory bridge, the AXI crossbar and the peripherals), and the same RTL missed again, by up to 0.35 ns. Most of the new failures came from one place: the dispatch handshake (does the ROB have room, did rename succeed, does each queue have a slot) decided whether the load/store queue and ROB entries were written, and that decision reached every bit of every entry. Now a free slot takes the incoming entry every cycle, and only its valid bit waits for the handshake. Nothing reads a free slot, so nothing changes. A few more of the same kind of fix, and an extra round of post-route optimization at the end of the build, closed the whole design at 174.998 MHz with 0.001 ns to spare. On the board it runs CoreMark at 900 per second (5.14 per MHz, up from 720 at 150 MHz), passes all 67 architecture tests and scores 2.25 per MHz on Embench at -O3.

The ROB is almost free to halve. The load queue holds each load until it retires, so it limits how many loads are in flight, and the store queue holds stores until they drain after commit; both cost the programs that already trail NaxRiscv. The scheduler is the most expensive. On timing, the 8-entry load/store queues closed 185 MHz with the core on its own (and saved 2,700 LUTs), while the 8-entry scheduler did worse, so the scheduler is not what limits the clock.

The board’s clock comes from the processor system, which can only make 175, 177.8 and 200 MHz in this range. 177.8 is too small a step to pay for a smaller queue, so the next real target is 200 MHz, and that needs more than shrinking: the single-cycle loops (an ALU result feeding the next ALU operation, a load address feeding the cache, the next fetch address feeding the instruction cache) would each need another pipeline stage.

A clock of my own¶

The processor system’s clock generator can’t make anything between 177.8 and 200 MHz, so I stopped using it for the core. The PL now takes the processor system’s 100 MHz and makes its own clock with an MMCM (a clock generator in the FPGA fabric), which can make almost any frequency. In the same round I gave the core’s synthesis a clock constraint (it had none before, so synthesis never knew which paths were tight), flattened the core’s hierarchy, and moved two rare events (a store’s response and a CSR write) a cycle later.

An MMCM also lets me finish a build at a slightly lower frequency without placing and routing it again: I change its output divider on the routed design and check timing at the new clock. The -0.149 ns build closed at 192 MHz that way, and with one more round of optimization at 195.9 MHz with no slack to spare. On the board, 195.9 MHz runs CoreMark at 1,008 per second (5.14 per MHz), passes the 67 architecture tests (one timer-interrupt test only when run on its own) and scores 2.25 per MHz on Embench at -O3.

Sizing the branch predictor¶

Wider tags did not help (9 bits -0.03%, 10 bits -0.48%). Dropping to three tables costs close to 1%, and a fifth table gains less than half a percent while making the logic that picks between the tables deeper, and that logic was already among the paths failing at 200 MHz.

Doubling every table to 2,048 entries was the biggest gain, and it only adds block RAM, so I expected it to be free. It wasn’t. The 200 MHz build with the bigger tables came in at -0.685 ns against -0.365 ns with the same RTL at 1,024 entries. Builds vary by about 0.2 ns from run to run, but that gap is larger, and about 0.3 ns is worth roughly 10 MHz. I kept 1,024 entries and took the better history lengths, which cost nothing.

Spending clock speed on IPC¶

Past 190 MHz, every remaining failing path is a loop that runs every cycle, and they all fail by about the same amount. Each fix moved the limit a few picoseconds, to the next loop. So I changed the order of work: performance per clock first, frequency last.

The reason is that the last bit of frequency doesn’t carry over. Closure (trying placement settings and extra optimization passes on one routed design) is tuned to that one netlist. The settings that took one 200 MHz build to -0.10 ns did nothing for the next RTL change: -0.365 ns before and -0.365 ns after. Any change to the RTL throws that work away, so it belongs at the very end.

Until then, I build every change the same way at a 200 MHz constraint and compare what it would close at. At these speeds 1% more instructions per cycle is worth about 1.9 MHz, so a change stays only if performance per clock times frequency goes up. The development builds must stay at 190 MHz or better, which keeps a few percent of frequency to trade. Changes that leave every cycle exactly as it was are always kept. The 195.9 MHz board build stays as the reference until a frozen design beats it on the board.

The first batch under this rule:

  • a divider that skips the steps it can tell will produce zero quotient bits (Embench +0.55%; ud, which divides a lot, takes 9.8% fewer cycles);

  • the better TAGE history lengths;

  • registers on paths that only matter rarely: the boot ROM’s output, the MMIO bridge and the UARTs;

  • two load/store queue paths reworked so they compute less in the cycle.

Together these gained 0.82% on Embench, left CoreMark unchanged, and gave the best 200 MHz build so far at -0.304 ns. After closure that design reaches about 192 MHz, below the 195.9 MHz board build, so the board build stays where it is for now.

Port 2 serves loads, stores, multiplies, divides and CSR operations. It used to give memory operations priority regardless of age, so a stream of younger loads could hold back an older multiply that everything else was waiting on. Taking the oldest ready operation of any kind sped up ud by 6% and needs one priority pick fewer.

The L0 is the small table that steers fetch in the same cycle. One Embench program, nsichneu, is a long stretch of code full of branches, and with 128 entries most of its taken branches missed and paid a cycle each. With 512 entries it runs 14.5% faster.

The bigger scheduler was the surprise. On every program but one it helped a little, but tarfind ran 55% slower. With more instructions in flight, a load ran ahead of a store to the same address often enough that the memory-ordering predictor told it to wait for every older store. The real cause is that a store here only computes its address once its data is ready too, so a store fed by a multiply resolves its address late. Splitting the two would fix it, but the gain left over did not pay for the larger scheduler.

Making a load’s result usable one cycle sooner was worth 3% on CoreMark, but checking for a cache hit in time to cancel the dependent instruction did not fit in one cycle: the build missed timing by 2 ns. Doing it properly means canceling and replaying everything issued in that window, which is a redesign for later.

Fusing instruction pairs¶

RV32 has no instruction that loads a full 32-bit constant, adds a shifted index, or zero-extends a halfword, so the compiler writes each as two instructions where the second overwrites the first. Macro-op fusion spots such a pair in decode and runs it as one operation. It saves a ROB entry and a scheduler slot, and when the second instruction waits on the first it saves a cycle too.

I kept only the first two. They need no new hardware in execute: the merged constant is still a lui, and the zero extend becomes an andi with a 32-bit mask. The other two need an extra shifter in front of the ALU’s adder, and that adder is in the loop that sets the clock. They were worth +0.16%, which is less than the clock they would risk. The 200 MHz build with fusion came in at the same timing as the build without it, for 255 more LUTs.

The gains are small because most of these pairs are not on the chain of instructions that sets the pace. crc32 is the exception. Its inner loop builds a constant and zero-extends a byte every pass, and it runs 4.8% faster. The loop counter and branch pair would matter most for CoreMark, but merging it puts an add in front of the branch compare, and that compare is on the slowest path in the core.

Splitting stores¶

A store here used to wait in the scheduler until both its address and its data were ready. While it waited, younger loads could not see its address, so they either guessed past it or waited. I split each store in two: the address half issues as soon as the base register is ready, and the store queue picks up the data later, from the address generator if it was already ready or from the result bus when its producer finishes.

For a core that is already more than twice NaxRiscv’s size, a percent of Embench was not worth it. It is not in the shipped build.

Per second the stack is slower: -0.7% on Embench and -3.1% on CoreMark, for a fifth more area. The reason is in the timing reports. On the worst paths, routing is 62 to 75% of the delay, and the logic itself is only 1.2 to 2.0 ns of the 5 ns cycle. The chip is a third full, so space is not the problem. Wire length inside the loops that must finish in one cycle is: wakeup and select, the forwarding muxes, rename, the load and store queue compares and fetch steering. Every one of these structures gets longer wires when it grows. On this FPGA, more hardware only pays when it stays out of those loops.

Loading a cycle sooner, properly¶

A load’s result is usable three cycles after its cache request. Making that two cycles was worth 4% on CoreMark in an upper-bound model, but the first version failed timing by 2 ns because the cache hit had to cancel dependent instructions in the same cycle. The second version checks the hit a cycle later, kills a wrongly woken instruction in the ALU instead, and gives every result that depends on an unverified load a two-bit mark that follows it through the fast wakeups, so a miss kills the whole chain.

Without the marks it was a loss (-0.4% on CoreMark), because dependents of a speculative instruction had to wait for the result bus. With them it gained 1.33% on CoreMark and 0.36% on Embench, but the build came in 0.47 ns worse, about 8% of the clock. It is not in the shipped build.

Reaching 200 MHz¶

The 195.9 MHz build came from an unusually good placement. Across twenty builds of later RTL at a 200 MHz constraint, the worst slack landed between -0.2 and -1.1 ns, usually around -0.5. Closure settings tuned to one netlist did nothing for the next, so I froze the RTL first: everything above that cost clock stayed out, and only fusion and the changes that cost nothing went in.

The third met every constraint at 200 MHz, the first time the whole platform has. On the board it runs CoreMark at 1,032 per second (5.16 per MHz), 2.4% above the 195.9 MHz build, and Embench at 2.31 per MHz, 4.8% above it per second, with all 67 architecture tests passing and every test retiring exactly the instructions the simulation retires.

One test needed a change to pass on the board. InterruptsSm raises interrupts through the timer’s memory-mapped registers and then idles a fixed number of loop iterations for each to arrive. Since the 195.9 MHz build, a register slice on the memory-mapped bus makes that store slower, while the larger L0 table makes the idle loop faster, so the interrupt arrived after the loop. The platform setting for that idle count went from 10 to 100 iterations.
