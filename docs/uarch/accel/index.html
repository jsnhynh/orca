FIN accelerator¶

FIN is ORCA’s matrix-multiplication accelerator. Its compute engine is a 16 by 16 weight-stationary systolic array. Signed INT8 activations and weights enter the array, each dot product accumulates in 32 bits, and an optional post-processing pipeline converts the result back to the signed INT8 range. FIN is verified in simulation and has not been brought up on an FPGA.

This page introduces the whole block and names every RTL file. The pages after it explain each piece down to its state, addressing and cycle behavior: Systolic array, Datapath, Control FSM, AXI interfaces and Hardware tiling.

The computation¶

FIN computes a matrix product:

A[M by K] x B[K by N] = C[M by N]

C[m,n] = sum over k of A[m,k] * B[k,n]

The names used in the RTL are:

  • A is the activation matrix;

  • B is the weight matrix;

  • C is the output matrix;

  • M selects output rows;

  • N selects output columns; and

  • K is the number of products in each dot product.

One physical array operation covers at most 16 M rows, 16 N columns and 16 K positions, and larger matrices are split into physical tiles. The array’s rows represent K positions, its columns represent N positions, and time carries successive M rows through the array. That mapping explains the transposed activation scratchpad in Datapath.

The multiply is signed 8-bit by signed 8-bit. Partial sums wrap in 32-bit two’s-complement arithmetic if they overflow; the array itself does not saturate. The normal output path adds an optional signed 32-bit bias, shifts, saturates to [-128, 127], optionally applies ReLU, and sign-extends that 8-bit result into a 32-bit output word. The raw path stores the full INT32 sum.

Two programming modes¶

The same controller supports two interfaces:

  • tiled mode describes one complete M x K by K x N job. Hardware validates it, walks M/N/K, handles edge tiles, and stores the final C matrix;

  • raw mode runs one 16 by 16 by 16 physical operation using the original source-address registers. Software may chain raw launches with acc_en.

Tiled mode is the normal interface for matrices larger than one physical tile. Raw mode is useful for small tests and direct array experiments. Neither mode changes the PE pipeline, and they differ only in how the controller selects addresses and whether another K tile follows.

The CSRs are generated from rtl/periph/peakrdl/fin/fin.rdl into fin_regs.sv and fin_regs_pkg.sv. Edit the RDL source and run make regs; do not hand-edit the generated files.

fin_pkg.sv fixes N=16, IN_W=8, ACC_W=32 and ACT_STRIP_K=1024. It also defines the typed bundles passed between modules. Keeping a DMA command or an SRAM write port in one structure prevents the address, data and enable of one operation from being wired independently by mistake.

The AXI-Lite target lets software configure FIN and inspect local data. The full AXI4 initiator moves complete rectangles between main memory and FIN’s scratchpads. They are separate because register accesses are short single-word operations, while tensor traffic benefits from bursts.

fin.sv gives a direct AXI-Lite scratchpad write priority over a simultaneous DMA write, and it gives the DMA output read priority over an AXI-Lite output read. No request queue sits behind either priority mux, so software must not modify or inspect scratchpads while a job is busy.

Lifetime traffic monitor¶

The separate traffic counters observe FIN’s AXI4 DMA port and AXI-Lite control port. They count accepted DMA bursts and beats, transferred DMA bytes, completed AXI-Lite reads and writes, and address-to-response cycles. These counters do not reset when a new job starts or when soft_rst is asserted. Clear while FIN is idle by writing 1 then 0 to traffic_control at 0x780; write 2 there to freeze a stable snapshot. Snapshot after bus transactions have drained. The BSP exposes this through orca_fin_traffic_clear() and orca_fin_traffic_snapshot(). Reads from the monitor’s own register range are excluded from the AXI-Lite counts so collecting a snapshot does not change it.

What one tiled job does¶

snapshot CSRs
    -> validate bounds and strides
    -> load one A row strip
    -> for each output-column tile:
         load optional bias
         for each K tile:
           load B -> preload weights -> compute/fold partial
         store one C tile
    -> repeat for the next output-row strip
    -> completion interrupt

A holds up to 16 rows across the complete K dimension, so it is loaded once per M strip and reused across every N tile. B changes for every (K,N) tile, and the bias changes for every N tile. The output scratchpad holds one 16 by 16 C tile while the K partials are accumulated.

The final K tile either passes through postproc.sv or stores raw INT32 data. The DMA then writes only the valid rows and columns, so edge padding stays local and never overwrites neighboring external memory.

Clocking, reset, and completion¶

All compute-side modules run on FIN’s clk and active-high rst. In a single-clock build, fin.sv directly wires both AXI interfaces to the core. With ORCA_FIN_MULTI_CLOCK, an AXI-Lite CDC bridge moves target requests from the fabric clock into FIN and a full AXI CDC bridge moves DMA traffic back to the fabric clock. No lower FIN module contains another clock crossing.

soft_rst returns the controller to idle and clears job-visible controller state, errors, counters, and done. It does not erase every scratchpad word.

On a successful job, irq is high during the one cycle in which the state is T_DONE. The sticky status.done bit becomes one on the following clock edge, when the controller leaves T_DONE, and remains set until another start or reset. On an error, irq is high during T_ERROR; err_pending, error, and done_id remain available after the controller returns to idle. See Control FSM for the exact priority.

Limits¶

  • N is fixed at 16 and tiled K is limited to 1024.

  • DMA, preload/compute, and output store phases do not overlap.

  • Only one DMA rectangle and one direct AXI-Lite transaction can be active.

  • The CPU cache and FIN DMA are not coherent, so shared buffers must use the uncached region described on the Memory page.

  • There is no floating-point, INT4, sparsity, or zero-skipping datapath.

  • Direct scratchpad access and an active DMA job are excluded by a software rule. The hardware does not arbitrate between them.
