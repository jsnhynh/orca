FIN systolic array¶

The systolic array is FIN’s arithmetic engine. It is a 16 by 16 grid of small multiply-accumulate cells. Data advances through registers instead of being broadcast through one large combinational circuit. This makes the hardware regular and keeps each clock cycle’s work small.

Related notes: FIN accelerator, FIN datapath, and FIN control FSM.

Files¶

File

What it owns

rtl/accel/array/pe.sv

one multiply/add cell and its stationary weight register

rtl/accel/array/skew_buf.sv

one delay line per array row

rtl/accel/array/sys_arr.sv

all 256 PE instances and the wires between them

The array uses the constants in rtl/accel/fin_pkg.sv: N=16, IN_W=8, and ACC_W=32.

How matrix coordinates map to hardware¶

For one physical tile, the array computes:

C[m,n] = A[m,0] * B[0,n] + ... + A[m,15] * B[15,n]

The hardware mapping is:

  • PE row r owns K position r and holds B[r,n];

  • PE column c produces N position c;

  • successive waves through time represent different M rows; and

  • the bottom of column c produces one C[m,c] partial sum.

Calling the design weight-stationary means each B[r,c] is loaded into a PE once before compute and remains there while many A values move from left to right. Partial sums move from the top of a column to the bottom.

One processing element: pe.sv¶

Each PE has five important registers:

  • weight_r holds the signed INT8 weight;

  • pipe_reg holds a signed 8 by 8 product represented in 32 bits;

  • a_pipe is the first activation-delay register;

  • v_sum_r holds the registered 32-bit vertical sum; and

  • a_out_r is the second activation-delay register.

The two compute stages are:

stage 1: pipe_reg <- signed(a_in) * signed(weight_r)
         a_pipe   <- a_in

stage 2: v_sum_r  <- pipe_reg + v_in
         a_out_r  <- a_pipe

a_out is delayed by two registers because the product takes one register and the add takes another. If the activation moved horizontally in one cycle while the partial sum took two stages, different products would meet the wrong partial sums.

The multiplier result is 16 signed bits and is sign-extended into pipe_reg. Addition is 32-bit two’s-complement addition. There is no overflow flag or saturation in a PE; any 32-bit overflow wraps. Saturation belongs to postproc.sv after the complete dot product.

PE control and reset¶

weight_ld writes weight_r independently of the compute pipeline. During preload=1, pipe_reg, a_pipe, v_sum_r, and a_out_r are cleared every cycle, while the selected PE row may capture a new weight. During compute_en=1, both arithmetic stages advance. When neither control is high, the registers hold their values.

The active-high rst clears the stationary weight and every pipeline register. Preload also clears the arithmetic state, so each physical tile starts with a zero partial-sum pipeline even though scratchpad contents are not globally reset.

Forming a wavefront: skew_buf.sv¶

The K rows cannot all enter at the same time. A product from array row 1 must meet the partial sum produced by row 0 one cycle earlier; row 2 must meet the sum from rows 0 and 1; and so on. skew_buf therefore delays input row r by exactly r enabled clocks:

array row 0: no delay
array row 1: one register
array row 2: two registers
...
array row 15: fifteen registers

Row 0 is a direct combinational connection. Each other row is a generated register array named pipe. The delay lines advance only when compute_en is high and clear only on rst. Values left from an earlier compute window can appear during the next warm-up, but the controller ignores array outputs until the new wave has completely filled the array.

This stagger changes a vertical wall of A values into a diagonal wave. That diagonal is why every K-row contribution for one output row meets the correct vertical partial sum.

Wiring the grid: sys_arr.sv¶

sys_arr first instantiates one skew_buf, then generates the 256 PEs with nested row and column loops.

Two wire networks connect them:

activation: a_h[r][c] -> PE[r,c] -> a_h[r][c+1]    left to right
partial sum: v_out[r,c] -> v_in[r+1,c]              top to bottom

a_h[r][0] receives skewed activation row r. Every top-row v_in[0][c] is tied to zero, which is the initial value of each dot product. The bottom row’s v_out[15][c] becomes psum_out[c].

weight_in[c] is broadcast down column c, but only PE row r captures it when weight_ld[r] is high. One-hot row loads avoid a combinational row-to-row preload chain. preload and compute_en are scalar controls shared by all 256 cells. The RTL contains no hand-built physical buffer tree; FPGA synthesis and placement may duplicate those high-fanout controls.

A small two-by-two cycle example¶

The real array is 16 by 16, but a two-by-two example shows the movement more clearly. Suppose one output row is [a0, a1] and the preloaded weights are:

        output column 0   output column 1
K row 0       b00               b01
K row 1       b10               b11

Ignoring the earlier SRAM-read cycle, the important compute edges are:

Edge

Events

0

PE[0,0] captures product a0*b00

1

PE[0,0] registers a0*b00; skewed a1 lets PE[1,0] capture a1*b10

2

column 0 registers a0*b00 + a1*b10; a0 has crossed PE column 0, so PE[0,1] captures a0*b01

3

PE[0,1] registers a0*b01; PE[1,1] captures a1*b11

4

column 1 registers a0*b01 + a1*b11

Column 1 finishes two cycles after column 0 because every horizontal PE hop has two registers. fin_datapath.sv delays column 0 by two cycles, so both answers emerge together at edge 4. In the 16-column array, column c is similarly 2*c cycles later than column 0.

How FIN schedules the array¶

Weights live in synchronous RAM, so preload counter 0 issues the first weight row read. Counters 1 through 16 assert weight_ld[0] through weight_ld[15]. The preload state therefore occupies counter values 0 through 16: one prime cycle plus 16 row-load cycles.

During compute, the activation RAM was already reading local M-row 0 during preload. Compute counter 0 consumes that row and requests row 1 for the next clock. The controller feeds 16 M rows, then leaves compute_en high while the last waves drain through the array and deskew registers.

For N=16, the controller’s fixed compute counter runs from 0 through 72. The first fully aligned C row reaches the datapath at counter 47 and the last at counter 62. Raw INT32 writes use counters 47 through 62. The three-stage post-processing path writes counters 50 through 65. Counters after the final write provide a simple conservative drain margin before the state changes.

Properties¶

  • The dimensions and generate loops elaborate a fixed 16 by 16 grid.

  • Every PE performs work during a physical tile, including zero-padded edge lanes; useful work is counted separately by valid_macs.

  • No PE performs sparsity detection, zero-skipping, rounding, or saturation.

  • compute_en stalls the PE and skew pipelines together. It is a phase enable, not a per-lane ready/valid interface.

  • The array has no AXI ports or address knowledge. Scratchpads and control translate matrices into its weight and activation vectors.
