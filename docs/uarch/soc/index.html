SoC¶

The SoC joins four active parts: the out-of-order CPU, FIN, memory and a few low-bandwidth peripherals. AXI is the common language between them. The CPU’s cache refill path is separate on purpose, because it moves a 128-bit backing-memory beat instead of a 32-bit AXI beat. Each 64-byte L1 cache block takes four of those beats.

This page explains the glue around the CPU and FIN. The Core and FIN accelerator pages cover the logic inside those blocks, and the Memory page covers storage and the address map. Interconnect, Peripherals and Platform have their own pages.

PS and PL are two different computers¶

The KV260 holds two processors. The processing system (PS) has hard Arm cores and PS DDR, and whatever runs on it is the host. ORCA runs RV32IMA payloads in the programmable logic (PL). ORCA has a 4 KiB boot ROM and no RAM of its own. Its programs and data live in a reserved 256 MiB window of PS DDR, cached through ddr_line_bridge, with a 16 KiB uncached DMA region at the top of the window (see the KV260 boundary). FIN is in the RTL and has been verified in simulation only, and no FPGA build enables it.

The host maps the host AXI aperture, stops ORCA, loads and reads back a payload, and then releases ORCA. The RISC-V CPU executes the payload, and the host supervises it.

Evidence: orca_pl_top.sv translates the host aperture, and the host simulation exercises loading, repeated launches and FIN jobs.

Limitations: those simulations do not run Arm software. A bitstream configures the PL and an XSA describes the hardware, and neither is a Linux image.

                                                       v

                                           |      |      |      |

A fifth page, the host console UART, sits beside the SoC CSRs. The Interconnect page lists all five.

The initiators are CPU uncached traffic, FIN DMA and the host, and the targets are memory and the peripheral branch. PULP’s source calls initiator-facing crossbar ports “slave” ports and target-facing ports “master” ports, because those names describe the crossbar’s own viewpoint. ORCA’s wrapper signals use initiator and target.

rtl/soc.sv: composition and reset ownership¶

soc instantiates one cpu, one memory, one fin, the two-level bus fabric, the UART, the timer and the SoC CSR endpoint. Most of the file is typed wiring. Its real state is the CPU stop control and, in a FIN multi-clock build, one reset synchronizer per clock island.

The module has core_clk and fin_clk ports. The CPU, the caches, the backing memory, the AXI fabric, the UART, the timer and the SoC CSRs all share core_clk. With ORCA_FIN_MULTI_CLOCK, each external reset passes through a local reset_sync, and otherwise the incoming active-high reset is used directly. The FIN IRQ is a registered FIN-domain signal that crosses into core_clk through two marked synchronizer flops. All other interrupt sources are already core-clocked. FIN latches an interrupt-pending level when it enters T_DONE or T_ERROR, and the level stays asserted until the next start, a soft reset or a reset. The two-flop synchronizer can therefore deliver it reliably even when FIN is faster than the core.

The SoC CSR reset value requests CPU stop. When HOST_CONTROLLED_BOOT is one, control.cpu_run == 0 or control.cpu_stop == 1 requests the stop lifecycle below. Memory, FIN, the AXI fabric, and the CSR block remain active while the CPU is stopped, so a host can load memory and configure a launch. When the parameter is zero, host controls do not request CPU stop.

Only two SoC status inputs are connected. cpu_stopped acknowledges the drained tile reset-hold, and cpu_running means the core is not held. Both are zero while draining. The return value, trap, failure, FIN completion, completion ID, mailbox and trap snapshot inputs are tied to zero in soc.sv. Cycle and retired-instruction values come directly from the CPU’s perf_stats. The boot stub reports completion through two words in the DMA buffer, in place of the tied-off CSR inputs.

CPU stop lifecycle¶

cpu_stop_ctrl.sv has three states: running, draining and held. A stop request immediately reset-holds the core pipeline and blocks new core requests. The router and caches stay clocked and keep their transaction state, and their responses are consumed while the held core ignores them. The controller waits until the router is idle, both caches and their response slots are idle, the line arbiter has no outstanding read, and fence maintenance is idle. Only then does it reset-hold the complete tile and assert status.stopped. Clearing stop during draining does not skip the drain or the reset edge that follows. Global reset still aborts the CPU and the fabric together. The controller adds no pipeline cycle in normal execution.

Interrupt wires are level signals. The timer supplies the machine timer and software levels. A writable validation register supplies an external level for the architecture tests, and the UART and FIN each supply an external level. The SoC synchronizes FIN’s level when its clock is separate. The CPU ORs the three external sources, so software must inspect the devices to learn which one asked for service.

Transaction examples¶

Host loads and launches a program¶

host AXI write at aperture 0x00100
  -> host address translation to ORCA 0x1fff_c100
  -> main AXI crossbar memory target
  -> ID remap and width converter
  -> shared DDR mux
  -> PS DDR (DMA region)

host writes boot_entry/run_id and sets cpu_run
  -> MMIO target
  -> full AXI to AXI-Lite
  -> peripheral crossbar
  -> soc_csrs
  -> core-clocked CPU run/stop control

The boot stub notices the new run generation, executes fence.i, calls the loaded entry, and then stores completion and the return value in the last two words of the DMA region. It never drives the tied-off done_id or mailbox inputs of soc_csrs.

FIN reads an input burst¶

FIN’s DMA request crosses into core_clk when needed, wins arbitration at the main crossbar, and reaches the DMA region through the ID remap and the width converter. Its 32-bit beats stay narrow on the 128-bit DDR bus. The shared DDR mux arbitrates it against the cache line bridge, so cache refill traffic can delay a DMA beat.

Reset summary¶

State

Reset behavior

CPU

core reset plus core-clocked host run/stop control

SoC fabric/peripherals

core-domain reset; remain live while CPU is stopped

FIN

FIN-domain reset; not controlled by CPU run/stop

AXI/PULP blocks

active-high ORCA reset inverted to active-low IP reset

boot ROM contents

initialized image remains; pending request clears

DDR contents

not cleared by reset; simulation benches load images into the DDR model at time zero

timer

counter zero, compare all ones, interrupt levels zero

generated CSR storage

RDL reset values; CPU run and stop both return to zero

Current limits¶

  • The KV260 build runs the CPU at 150 MHz.

  • The host aperture reaches only the DMA region and MMIO. The host loads everything else directly into DDR through the processing system, while the CPU is stopped.

  • There is no cache coherence, so data shared between the host and FIN belongs in the uncached DMA region.

  • ORCA reaches PS DDR through the cached line bridge and through the uncached DMA region, and the host reaches the DMA region through the PS-to-PL AXI path.

  • Several SoC status CSRs are placeholders tied to zero, so the host protocol uses the DMA completion words.
