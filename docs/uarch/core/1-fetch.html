Stage 1: Fetch¶

Fetch turns a predicted PC into instruction bits. On paper that is a FIFO and an SRAM read. In practice it is the most intricate stage in the core, because it is the one place where a multi-cycle cache, a two-speed predictor and four different flush sources all have to agree on which bytes are real. Most of the odd-looking registers on this page exist to keep that agreement.

Related notes: Stage 0: Branch prediction, Stage 2: Decode, L1 caches and Memory.

Shape¶

        pc ──> imem_req ──> I-cache ──(n cycles)──> imem_rec
                                                       │
                                            predecode ─┤
                                            hold reg  ─┤
                                                       v
                                              inst_buffer (4 deep)
                                                       │
                                                       v
                                                    decode

Two instructions per request, aligned to an 8-byte group. When pc[2] is set the group only has one valid lane, so direct_resp_vals is 2'b01 instead of 2'b11.

Predecode¶

predecoder.sv looks only at opcode, rd, and rs1. It recognizes conditional branches, JAL, and JALR before full decode, and classifies writes to x1 or x5 as calls and a JALR x0, (x1|x5) as a return. It does not decide whether an encoding is legal; decode owns that check. Fetch uses this early classification only to allocate FTQ metadata, update speculative history, and remove an unreachable younger lane.

Request launch¶

imem_req_val is asserted whenever the downstream window has room, and effective_pc_next picks the address by priority:

pred_redirect_val   -> pc_next          (L1 repair, from the BPU)
flush_pending_q     -> flush_target_q   (latched architectural redirect)
startup_q           -> PC_RESET
next_req_pending_q  -> next_req_pc_q    (deferred successor)
otherwise           -> pc_req_next      (fallthrough or L0 target)

Two of these need a word of explanation.

flush_pending_q. A redirect target is only driven on pc_next during the flush cycle itself. If the I-cache cannot accept a request that cycle, the target would be lost and fetch would resume at pc+8. So the target is latched and re-driven until the request actually fires.

next_req_pending_q. When a response is accepted but no request can go out in the same cycle, the successor PC belonging to that packet’s FTQ entry is held and used for the next request.

Ordinary launch does not wait for the late L1 prediction. Registered instruction-buffer and FTQ occupancy are enough to reserve a slot. If L1 later redirects, the speculative request is killed and replaced in exactly the cycle a non-speculative scheme would have launched the correct one, so nothing is lost. The payoff is that the response bits -> predecode -> req_valid -> I-cache address path does not exist.

Response handling and the hold register¶

When the L1 predictor says a fetch group ends in a taken branch, that group cannot be pushed downstream immediately, because the redirect and the packet have to leave together with matching metadata. hold_q parks the whole packet (PC, lane valids, instruction bits, prediction metadata) for one cycle:

hold_capture = pred_hold && imem_rec_val && imem_rec_rdy && !flush && !hold_q
hold_release = hold_q && inst_buffer_rdy && alloc_rdy && !flush
selected_val = hold_q ? hold_release : direct_push

While a packet is held, imem_rec_rdy drops to zero so the cache backpressures and no second response is dropped. If a redirect arrives while the packet is still held, the prediction metadata is refreshed from the new bpu_pred so the FTQ entry stays consistent with what was actually predicted.

Fetch has no response-side epoch filter. The L1 subsystem guarantees that kill removes every stale response, and response PCs travel with the cache data and are never rebuilt from the newest request. A response can therefore always be trusted to belong to the request that is still live.

Lane scrubbing¶

Predecode runs on the selected packet and kills younger lanes that are architecturally unreachable:

slot0 is an unconditional transfer           -> resp_pc_vals = 2'b01
slot0 hits BTB as taken (or non-conditional) -> resp_pc_vals = 2'b01

The unconditional case matters even without a BTB hit. A cold JAL or JALR has no prediction yet, but slot 1 is still unreachable and must not receive an FTQ entry. Killed lanes have their instruction bits zeroed so that consumers which only check fetch_vals cannot see garbage.

FTQ allocation¶

For every valid lane that predecodes as a branch, fetch builds an ftq_alloc_t carrying the branch PC and its prediction. On a BTB miss the predecoded branch type is substituted, so the FTQ still knows whether it is looking at a call, a return, or an ordinary jump.

Direct targets¶

A JAL or a conditional branch holds its own target: the PC plus an immediate in the instruction word. So fetch does not need the BTB to learn where these go. When the I-cache response arrives, fetch.sv adds the immediate to each lane’s PC (direct_target in fetch.sv) and hands the result to the branch predictor as pred_direct. It carries a valid bit, whether the instruction is a JAL, the branch type (a JAL that writes x1 or x5 is a call) and the target.

The predictor uses it only when the BTB has no entry for that lane. A JAL is then predicted taken to the computed target. A conditional branch takes the TAGE direction and, when TAGE says taken, the computed target. The prediction is recorded in the FTQ exactly like a BTB hit, so execute and commit check it the way they check any other prediction. It reaches the request stream through the L1 repair described on the branch page, so a computed target costs the same one-cycle bubble as an L0 miss. A BTB hit always wins over the computed target. JALR and returns still need the BTB or the RAS, because their target is not in the instruction.

The cost is one adder per lane on the response path. The gain is that a branch’s first encounter, and any branch the BTB has evicted, no longer costs a full redirect from execute. A small BTB therefore loses less than it would without it.

alloc_accept is the architectural handshake, and the candidate payload is built unconditionally. Keeping recovery control out of the payload path lets the FTQ precompute its data without broadcasting flush through every bit.

Instruction buffer¶

A plain 4-entry circular FIFO. One entry holds an entire fetch group: base PC, lane valids, FTQ valids and IDs, and both instruction words. Decode reads buff[rd_ptr], splits it into two lanes, and derives inst_pcs[1] as pc + 4. The buffer head feeds decode, whose output is registered before rename (decode register).

Its job is decoupling. The cache has variable latency and decode has variable backpressure, and without the buffer every decode stall would immediately stall the cache.

inst_buffer_rdy is ~is_full || flush, and both pointer updates are qualified with !flush so a flush cycle cannot move data. The read data itself is not gated by flush. In a flush cycle the buffer may still present its head group, and the decode register clears on flush. Gating the read mux would put the architectural redirect at the head of the decode, rename, dispatch and queue-insertion chain, so the data path is left ungated. The fetch benches check that the buffer is empty from the edge that ends the flush cycle.

The FIFO uses independent read and write pointers plus a count. A simultaneous push and pop leaves the count unchanged. A full FIFO does not credit a same-cycle pop as new input space, so upstream waits one cycle. That keeps decode readiness out of the cache request path. Reset clears payloads as well as pointers, while a flush only resets pointers and count because invalid payload bits are unobservable.

Backpressure¶

fetch_window_rdy = inst_buffer_rdy && alloc_rdy
imem_rec_rdy     = hold_q ? 0 : (pred_hold ? 1 : fetch_window_rdy)
imem_req_val     = !flush && (hold_q ? release-with-redirect : fetch_window_rdy)

A held predicted-taken packet can still be captured while the downstream window is full. In that case no speculative request is launched until the packet can be released; the hold register itself provides the storage.

Flush behavior¶

flush clears the instruction buffer pointers and the hold register, kills the in-flight cache access via icache_kill, and blocks request launch for that cycle. An assertion checks that no request fires during architectural recovery:

assert (!(flush && req_fire))
    else $fatal(1, "FETCH: request fired during architectural recovery");

Known limits¶

  • Hold storage is one fetch group deep, so a second consecutive predicted-taken group backpressures the cache.

  • No fetch-target-buffer style multi-group prediction: one group per request.

  • Misaligned groups always waste the upper lane.

  • The instruction-cache interface has no error bit, so this stage cannot create an instruction access-fault report.

Tests¶

sim/cpu/tb/1-fetch/fetch_tb.sv tests the unit alone. sim/cpu/tb/1-fetch/fetch_int_tb.sv tests the integrated predictor, cache and redirect interaction.
