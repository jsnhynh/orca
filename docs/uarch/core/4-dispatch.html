Stage 4: Dispatch¶

Dispatch steers each renamed instruction to a scheduler entry and, for memory operations, a load or store queue slot, and it writes the ROB entry. It shares the rename cycle: queue write enables come from registered queue occupancy, so there is no pipeline register between rename and the queues.

Related notes: Stage 3: Rename, Stage 5: Issue and Core.

Classification¶

Every instruction without an exception enters the 16-entry scheduler (RS_ALU). Loads, stores and atomics also take a slot in their queue:

Class

Goes to

RS_ALU

the scheduler: ALU, branch, multiply/divide, CSR and memory address generation

RS_LD

also the load queue

RS_ST

also the store queue (stores and atomics)

 
c[RS_LD]  = (opcode == OPC_LOAD);
c[RS_ST]  = (opcode inside {OPC_STORE, OPC_AMO});
sched_slot[s] = is_valid && !exception;   // every slot with work

core.sv stamps each scheduler entry with an issue class taken from the opcode: UOP_CLASS_MDU for multiply/divide, UOP_CLASS_SYS for CSR, UOP_CLASS_MEM for loads, stores and atomics, and UOP_CLASS_ALU for the rest. The scheduler uses the class to choose the issue port. The RS_MDU and RS_SYS constants stay in the packets, but no queue exists behind them.

An instruction that already carries an exception classifies as nothing. It still gets a ROB entry, because precise traps need it in program order, but it never occupies an issue slot or an execution unit.

Branches take ordinary ALU-class scheduler entries. Only two physical operand IDs and their readiness are queued. Issue reads the values and the PC and immediate context to rebuild the unit’s two operand pairs, and one ALU computes the target and the condition together.

Routing¶

Rename compacts a lone valid instruction into slot 0, so routing has only two cases:

both slots target the same queue  -> slot 0 to channel 0, slot 1 to channel 1
different queues                  -> each to channel 0 of its own queue

The scheduler is routed separately. Slot 0 takes lane 0, and slot 1 takes lane 1, or lane 0 when slot 0 carries an exception. A load or store is accepted only if both its scheduler lane and its queue channel are free, and the group is all-or-nothing.

Payloads are routed before write enables are applied, so the mux does not wait on the readiness decision:

rs_issue_ports[rs][0] = slot_rs[0][rs] ? renamed_insts[0] : renamed_insts[1];
rs_issue_ports[rs][1] = renamed_insts[1];

core.sv then attaches each port’s scheduler record and payload. It picks the source lane from the decode register: lane 0 when that lane targets the queue or the group compacts, and lane 1 otherwise. The ROB grant gates only validity, at the end. Picking the lane by comparing the port’s ROB tag with each renamed lane’s tag would let the ROB grant reach the payload mux, the wait-table lookup and the scheduler fields through a 6-bit compare, so the lane comes from the decode register instead. A written port implies a grant, and then decoded and renamed validity agree, so both methods give the same lane. A simulation assertion checks that on every written port.

Backpressure¶

One handshake covers rename, ROB allocation and queue insertion:

rename + dispatch --dispatch_rdy--> scheduler / load queue / store queue
                           |
                           +-- write ROB, write payload

The rs_rdys seen by dispatch.sv come straight from the target queues’ registered free slots. A slot freed by an issue at this edge becomes visible on the following cycle, so queue readiness never depends on same-cycle selection.

dispatch_rdy also requires the ROB grants reserved during rename. It is the single signal that stalls the whole front half of the machine. rob_rdy[1] and rob_rdy[0] handle whether slot 1 follows a valid slot 0 or is the only instruction in the compacted group.

Group acceptance, ROB allocation and queue insertion are atomic. Either every instruction in the group is placed in this cycle or none is.

ROB entry writes¶

Dispatch writes the ROB entry in the same cycle that rename receives the tag:

rob_we[s]      = dispatch_rdy && renamed_insts[s].is_valid;
rob_entries[s] = gen_rob_entry(renamed_insts[s]);

The entry carries only what commit needs: PC, rd, has_rd, opcode, uop_0, csr_id and the exception flag. Operand values are not stored, and the result comes back on the CDB later.

core.sv separates the allocation packet’s immutable fields into uop_payload_t. The sibling payload_array stores them by granted ROB ID, and the ROB stores only rob_state_t. The payload array’s accepted-allocation write enable keeps the two stores atomic through reset, backpressure, flush and recovery. It writes the execution controls, the immediate, the physical destination and the FTQ identity into the 106-bit context. core.sv routes only narrow uop_entry_t packets (20 bits plus the ROB tag) into the integer scheduler. The wide instruction_t is the decode and switchyard interface and the form that issue rebuilds for execution, and it is never the stored scheduler entry.

Payload array storage¶

The payload array uses one single-writer distributed-memory bank per dispatch lane and a per-ROB-ID last-writer selector. The three retirement one-hot read requests are encoded into addresses, and the eight issue and insertion ports supply binary ROB IDs and enables directly. Both banks are read asynchronously, and the current writer’s bank is selected. Both writes may target arbitrary distinct ROB IDs, and no parity is assumed. There is no write-through bypass: a read sees the previous context before the allocation edge and the new context after it. Reset inhibits writes but keeps both the data and the writer identity, because ROB validity owns context lifetime. uop_q is a simulation-only view used by the retirement and debug oracles, and it is not a synthesized array.

The payload bench checks all eleven read ports, switching writer lanes, same-parity addresses and reset retention. The bank’s storage declaration is a flat vector on purpose, because Vivado does not infer a RAM from a packed-struct declaration with the same behavior.

Exception reports go out on a separate rob_exceptions port carrying the ROB tag, the cause and tval, so the ROB can track the oldest pending exception independently of entry completion.

Wakeup during insertion¶

A CDB broadcast that wakes a source is seen exactly once. Rename reads a source’s busy bit and the same-cycle PRF write ports, so a producer that completes in the rename cycle marks its consumer’s source ready. A producer that completed earlier is already visible in the busy table. A producer that completes after the consumer is queued is caught by the scheduler’s own wakeup. No broadcast is lost, because there is no cycle in which an instruction is renamed but not yet visible to wakeup.

Recovery¶

Branch recovery blocks allocation for the recovery cycle (rename_ready drops while recovery.val), so no group is inserted that the same recovery would squash. Queues remove entries younger than the resolving branch using circular age against rob_head: subtract the head from both tags and compare the distances, so wraparound needs no epoch bit. full_flush clears everything. It covers commit-time prediction recovery and architectural redirects such as traps, MRET and FENCE.I.

Known limits¶

  • Nothing buffers between rename and the queues. A group whose target queue has too few free slots stalls rename.

  • Queued multiply/divide operations share the integer scheduler’s channel pair with ALU work, and they issue through port 2 on separate cycles.

  • Dispatch does no load/store dependence prediction of its own. A load that has conflicted with a store before is held back by a one-bit wait table indexed by load PC (see Stage 5: Issue).
