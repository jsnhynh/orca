Branch Prediction¶

The predictor, SONAR, picks the next fetch address every cycle. It has four parts:

  • the BTB (branch target buffer) remembers where a control transfer went,

  • TAGE predicts which way a conditional branch goes,

  • the RAS (return address stack) predicts return targets,

  • the FTQ (fetch target queue) keeps what execute and commit need to check each prediction and undo a wrong one.

The RTL is in rtl/cpu/0-branch/, and the sizes are in rtl/cpu/common/branch_pkg.sv.

Two Speeds¶

The BTB and TAGE live in block RAM with a one-cycle read, but the next I-cache address has to leave this cycle. So SONAR runs two predictors.

cycle n     pc ──┬──> L0 BTB (LUT RAM) ─> immediate redirect target
                 └──> BTB + TAGE + RAS (SRAM) ─┐
cycle n+1                                      └──> L1 verdict
                                                     agrees?  keep going
                                                     differs? hold + repair

The L0 is a 512-entry LUT RAM table that answers in the same cycle, so a taken branch it has learned costs no bubbles. The L1 (BTB, TAGE, RAS) answers a cycle later with the I-cache response. If they disagree, or the L0 missed and the L1 says taken, the packet holds for a cycle and fetch repairs. That one bubble is the price of an L0 miss.

The L1 Verdict¶

A 4-entry metadata FIFO runs beside the I-cache requests. A request reserves a slot with its PC, the L0, BTB and TAGE results fill it a cycle later, and the I-cache response takes it from the head. The FIFO also keeps the address fetch asked for next, since the L0 can retrain while a request stalls.

The L1 checks every response and skips the repair only when the L0 and L1 agree and the next requested address is the predicted target. Any packet whose next address is still unknown repairs. That rule came from the one bug that changed the design (verification).

With no BTB entry, fetch computes the target from the instruction, so a JAL or a branch TAGE calls taken still predicts taken. A BTB hit wins over the computed target.

L0 BTB¶

Each entry covers one 8-byte fetch group, indexed by pc[11:3]: a valid bit, an 8-bit partial tag, a slot bit, a 2-bit strength counter and the target.

taken     + miss  -> install, strength = 2
taken     + hit   -> strength++ (saturate at 3)
not-taken + hit   -> strength == 3 ? demote to 2 : evict
return            -> trains like a taken jump (L1 checks it against the RAS)

A saturated entry survives one not-taken, so a loop exit doesn’t throw the entry away. The metadata is one LUT RAM word with two async reads (lookup and training). The target is a second LUT RAM written only on an install, so it needs one read port. Neither is reset; a sweep clears the table after reset and the L0 just misses for those 512 cycles.

Why a partial tag. Two fetch groups can alias on 8 bits, but the L1 checks every L0 prediction, so an alias costs one repair bubble and never a wrong path. With the valid bit in the RAM word too, the entry went from 55 bits plus 512 valid flops to 42 bits, and the L0 from 1,838 to 834 LUTs, for 0.016% more CoreMark cycles from the reset sweep.

BTB¶

512 entries, 256 sets of 2 ways, split across two block RAM banks by the low index bit so both words of a fetch group read in one cycle. The index is pc[9:2] ^ pc[17:10]. Two ways keep two hot branches in one set from evicting each other.

The victim way is picked at prediction time and carried in the FTQ, so training never rereads the table. Only taken branches install, at commit, one a cycle.

TAGE¶

TAGE has a 512-entry base table and four tagged tables of 1,024 entries over 4, 10, 24 and 64 bits of global history. The longest table with a matching tag gives the prediction (the provider), and the next longest is the alternate. A tagged entry is a 3-bit counter, a 2-bit useful counter, an 8-bit tag and a valid bit.

History shifts at fetch, for conditional branches only. A shift counter gives every history a 6-bit position, and LUT RAM keeps the history that stood at each position, so an FTQ entry only stores the position and a mispredict reads the old history back. Another LUT RAM keeps the folded histories by position, so training reads the folds its branch was predicted with instead of folding again.

Why positions instead of history copies. Each FTQ entry used to hold two 64-bit histories. The positions take 12 bits, and the FTQ went from 1,644 to 988 LUTs while TAGE grew by 77, with the same cycle counts.

Training happens at commit, one branch a cycle: update the base table and the provider, and on a provider miss allocate in a longer table with a free entry (picked at prediction time). Useful counters age the old entries out.

Why direct table writes. Training builds the new word from the counters its branch was predicted with and writes it straight in. Two updates to one entry back to back keep only the second. The old pending-write and forwarding logic cost 704 LUTs and 440 registers in the four tables, and dropping it moved CoreMark by -0.06% cycles and Embench by +0.01%, with aha-mont64 the worst at +2.3%.

Why this size. A sweep over table count, size and history length picked it. Longer history helped most, mainly on loop exits with other branches inside. A 128-bit history with 512-entry tables was about as good but needed twice the history storage. The block RAM tables aren’t reset; a sweep zeroes them after reset.

RAS¶

A call pushes pc+4 and a return pops, over 16 circular entries. Each FTQ entry saves the stack pointer for recovery. A wrong-path call can overwrite an entry a wrong-path return just popped, and the return that reads it later mispredicts once. Saving the top entry in every FTQ entry would cost more than those rare misses. The top two entries sit in flops, which keeps a 16-way mux off the fetch path.

FTQ¶

Execute and commit need what the predictor knew: PC, prediction, provider, history position and RAS pointer, over 100 bits. Only control instructions need it, so they get their own 16-entry queue instead of widening the ROB.

  • Allocate: each fetch packet enqueues one entry per control instruction, up to two a cycle.

  • Execute: the ALUs look up their entry and compare. A mismatch redirects the front end, and the back end flushes when the branch retires (recovery).

  • Commit: the oldest entry dequeues, trains the BTB, TAGE and L0, and checks the outcome once more as a backstop.

An entry is live when its distance from the head is below the count, so there are no per-entry valid bits. Each enqueue lane writes its own 16-entry LUT RAM, and a bit per entry says which lane wrote it last.

Why per-lane RAMs. Two 16-entry RAMs cost the same LUT RAM as two 8-entry parity banks, and they remove the swap mux in front of the writes (102 LUTs out of fetch, 66 into the FTQ). One array with two write ports had put a 2,000-flop mux on the recovery path.

All four are registered. Training only happens at commit, since execute may be on the wrong path.

Limits¶

  • No indirect target predictor beyond the BTB, so a call through a changing pointer mispredicts.

  • A RAS entry overwritten on the wrong path stays overwritten.

  • The L0 is direct mapped, so big code footprints conflict.
