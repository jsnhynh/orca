Stage 5: Issue¶

The scheduler waits for operands and then selects ready work in age order, not program order. The ROB still retires in program order. This stage also holds the load/store queues, which is where most of the memory-ordering logic lives.

Related notes: Stage 4: Dispatch, Stage 6: Execute, Stage 7: Writeback, L1 caches and Stage 3: Rename.

Queue integration¶

issue.sv instantiates one scheduler and the load/store queues. The scheduler stores narrow uop_entry_t records (32 bits: a ROB tag plus readiness, class and fast-wakeup destination) and never stores instruction_t operand values. Each record carries an issue class: ALU/branch, multiply/divide, CSR or memory. The issue wrapper reads immutable controls from payload_array, and physical values from the PRF, only after selection.

Every load and store takes both a scheduler entry and a load-queue or store-queue slot at dispatch. The scheduler issues it on port 2 like multiply/divide work. Register read supplies the base register, the immediate and, for a store, the data register, and the AGU (slot 3) computes the address. The AGU result fills the queue entry by ROB tag. The queues hold no operands and see no CDB traffic.

Six PRF read ports provide four operands for ports 0 and 1 and two for port 2. Three issue-side context ports serve the three scheduler ports. Load and store insertion take the payload being written in that cycle and do not read it back. Three other context ports belong to retirement.

Readiness on port 2 depends on the selected class. Memory work advances whenever the AGU accepts, which is always. Multiply/divide and CSR work advance when both of those units accept. The class comes from the registered selection, so the handshake never depends on the payload read. Issuing from the queues to memory needs both the LSU request path and result-holding capacity, and their readiness signals are ANDed before they are exposed as dmem_rdy.

The integer scheduler¶

scheduler holds up to 16 entries. Each entry has a valid bit, a ROB ID, two six-bit physical source IDs, source use and readiness bits, and an issue class. The PC, immediate, destination and operation controls are in the shared payload array.

Port 2 serves multiply/divide, CSR and memory work together. It takes the oldest ready memory entry, and otherwise the oldest ready multiply/divide or CSR entry. A CSR entry waits at the ROB head, so younger memory work cannot starve it beyond a full load/store queue. CSR entries are ready only when their ROB ID equals rob_head. A store is ready when both its base and data registers are ready.

Resident wakeup¶

A qualified CDB physical destination sets the matching readiness bits. Held entries capture that readiness, so backpressure cannot lose a one-cycle broadcast. Same-cycle resident wakeup stays enabled:

entries_woken[e] = wake_uop(entries[e], cdb_ports);
entry_ready[e] = !rst && !flush && !recovery.val && entries[e].is_valid &&
    (!entries[e].rs1_used || entries_woken[e].rs1_ready) &&
    (!entries[e].rs2_used || entries_woken[e].rs2_ready);

New allocations register before selection, and a coincident completion is captured at insertion. Only accepted, successful physical writes wake consumers. Reset, flush and recovery suppress issue. Recovery discards only younger ROB lifetimes, and issue clears validity without changing physical register ownership.

Age and selection¶

A pairwise matrix records allocation order across all classes. Of two live entries exactly one is older, so only the upper triangle is stored (older_than[a][b] for a < b) and the other order is its inverse. Among ready ALU entries, the one with no older ready ALU peer has rank zero, and exactly one older ready peer means rank one. Ports 0 and 1 take these ranks according to FU availability. Port 2 takes the ready multiply/divide, CSR or memory entry with no older ready peer of those classes.

Allocation sees only registered empty slots, not same-edge issue space. New lifetimes are younger than all survivors, and dispatch lane order breaks ties. Recovery and issue remove the old lifetime from the order bits before the next registered state. The focused timestamp bench checks one, two and three issue ports independently, plus head-only ordering, wakeup, stalls and recovery.

Register read after selection¶

issue.sv routes every scheduler selection through register_read before it presents source IDs to the combinational PRF read ports and binary ROB IDs to the context reads. Ports 0 and 1 go through alu_register_read and port 2 goes through aux_register_read. This adds one issue-to-execute cycle to multiply/divide, CSR and memory work. Multiply/divide packets take both register operands from the PRF, so PC and immediate selection is not needed for them. An AGU packet carries the base register, the immediate and the store data.

The IDs are not decoded into one-hot vectors for the array to re-encode. Disabled reads address entry zero and return zero, and there is no speculative ungated context read. Retirement keeps its three one-hot selectors. materialize_uop rebuilds the FU packet: register operands come from the PRF, and the PC, immediate and controls come from the 106-bit payload. Branches get register comparison operands and PC/immediate target operands from these two sources.

register_read.sv holds one 25-bit accepted selection per ALU lane. In the following cycle it reads PRF values and context in parallel and forms the packet for the ALU input register. A lane accepts when it is empty or when its current packet can enter the ALU. Same-edge consume and replacement allows two independent selections per cycle with no forced bubble. Under backpressure the selected identities hold, and the scheduler removes an instruction only on an accepted selection. Reset and full flush clear both lanes. Recovery disables reads, input acceptance and visible output for that cycle, removes younger selections and keeps older ones, and transfers resume afterward. This also stops the ALU’s register-enable logic from capturing work during its recovery-qualified ready=0 interval.

Accepted-write PRF bypass stays available during operand read. Fixed-latency integer ALU operations also announce their physical destination on an accepted register-read-to-ALU transfer. The scheduler can select a dependent in that cycle, and the dependent’s following read cycle receives the producer’s computed value through forwarding. Loads wake speculatively (below). Branches, jumps, multiply/divide and system operations wake on actual completion. Fast tags also apply at enqueue. They do not clear rename busy bits, write the PRF or complete the ROB.

The announced destination travels in the scheduler entry (fast_pdst, set at dispatch from the payload for fast ALU operations and zero otherwise). It does not come from register read’s payload-array read, which keeps the payload LUTRAM read out of the select, announce, wake, select loop.

Each ALU forwards both its current computation and its held output, so announced values stay available when CDB grants or consumer acceptance stall. Forwarding rejects exceptions and physical register zero, and recovery suppresses transfers and killed producers. The computation starts from registered ALU operands, not the current read packet, so there is no unregistered chain through multiple ALUs. Source values and ROB payloads must stay live while a selected instruction waits. Normal in-order retirement prevents a younger writer from freeing its source physical register before the waiting reader completes.

Speculative load wakeup¶

The LSU announces spec_wake for a cache-path load in the cycle after its request is accepted. The scheduler treats it like a fast wakeup for ALU, branch and memory consumers, which are selected in the cycle the data is expected. The multiply/divide and CSR classes do not wake early. The announcement is a promise made before the hit is known, so a selection that depended on it carries a flag, and the outcome arrives one cycle later as spec_check:

  • Hit. The consumer’s scheduler entry, which was kept for that one cycle, is freed. Its operand comes from the LSU result register through register read’s forwarding input, because the register file is not written until the CDB grant.

  • Miss. Register read drops the selection, and the scheduler takes back the readiness the wakeup gave (cancel) for every entry waiting on that register. The entry never left the scheduler, so it keeps its age and re-issues when the real result is broadcast. The drop also applies in a recovery cycle, when the lane is otherwise frozen, because the check does not repeat.

Entries that were not selected in the wake cycle but were marked ready by it are covered by the same cancel. A selection held in register read by a busy functional unit clears its flag after its first cycle, because that is the only cycle its check is valid.

spec_wakeup_tb drives the real scheduler, register read and register file against a model load unit with hits, misses, delayed grants, a single result register and recovery pulses. It checks that every transfer carries real operand data, that every uop transfers exactly once, and that the scheduler drains. It fails if the register-read kill or the readiness cancel is removed. The CoreMark oracle and GEMM64 check the same behavior end to end.

CSR and system work¶

CSR and system entries issue only when entry.rob_id == rob_head. They then read their source through port 2 and enter the CSR unit, so architectural CSR state stays non-speculative.

Load/store queue¶

lsq.sv owns the two queues, memory disambiguation, store-to-load forwarding, store draining and a two-cycle recovery sequence. It does not schedule address generation or track operands.

Structure¶

  • Load queue. 12 entries in a circular FIFO (ldq_head, ldq_tail, ldq_count). Loads allocate at the tail in dispatch order (a lone second-lane load takes the first slot, so there is no hole) and free as they retire. The head advances over leading entries that are free this cycle, and branch recovery rolls the tail back past the killed loads in the cleanup cycle. Loads issue out of order, and age is the distance from the head.

  • Store queue. 12 entries in a strict circular FIFO (stq_head, stq_tail, stq_count). Stores must drain in order, and age is the distance from the head.

  • Order. Load against load and store against store come from FIFO position. The head pointer is turned into a thermometer code (head <= x), and entry j is older than entry i by two gates on those bits. Load against store is a count: ld_older_cnt[ld] is how many stores were queued when the load allocated (plus the earlier stores of its own dispatch group, found by a tag compare per dispatch channel), and each store pop counts it down. The stores it counts are the oldest in the store FIFO, so store st is older than the load when its distance from stq_head (stq_pos[st]) is below the count. A store killed by recovery is younger than every surviving load, so recovery and flush need no handling here. A simulation-only age matrix runs beside this order, and an assertion checks that the two agree for every pair of live entries in every cycle.

The order state is one small count per load plus FIFO pointers. A full age matrix would need 576 bits, and the logic that reads the FIFO order is simpler.

Each entry also has side state: agu_comp (the address, and for stores the data, has arrived) and, for stores, committed (authorized by the ROB). A load entry holds validity, ROB ID, physical destination, access size and sign, an issued flag, a wait_older bit, a 4-bit load-PC hash and a 32-bit address. Store data is not in the entry: the 32 bits per store sit in a small LUT RAM (stq_data_mem) that is written when the AGU result arrives and read in only two places, the store at the head and the forwarding select. load_entry and store_entry take the identity fields at insertion, and load_packet and store_packet rebuild the LSU interface at issue with queue-implied opcodes. Load selection stays one-hot through the compact payload mux. Simulation assertions reject a live non-load or non-store inserted into the matching queue. Precise exception PCs come from the ROB. The simulation-only stq_pc keeps each store’s PC for traces, including committed stores that outlive their ROB context.

A load is marked issued when it is selected either for a cache request or for store-to-load forwarding, and the LSU then owns any outstanding request or CDB backpressure. The load keeps its entry until it retires, so a store whose address arrives later can still be checked against it. Retirement comes from the core’s retire ports (retire_valid, retire_ids), sampled a cycle late, so the commit count never reaches the queue’s state. A store leaves the store queue when its authorized memory request is accepted, and the ROB, the LSU and the saved ROB tag keep retirement waiting for the write response. Leaving the queue therefore does not mean the store has retired.

Address generation¶

The scheduler issues a load or store on port 2 once its registers are ready. Register read forms the AGU packet, and the AGU computes the address in the next cycle. The result returns by ROB tag, with the store data alongside:

if (stq[e].is_valid && !stq_agu_comp[e] && stq[e].dest_tag == agu_result.dest_tag) begin
    stq_next[e].addr = agu_result.result;      // the data goes to stq_data_mem[e]
    stq_agu_comp_next[e] = !agu_result.exception;
end

Only the first result completes an entry. A faulting (misaligned) result leaves it incomplete, and the ROB’s exception flushes it. Disambiguation and memory issue read ldq_addr_ready_comb and stq_addr_ready_comb, which are derived from registered entries, so the AGU adder never reaches the cache request. Memory work uses the scheduler, register read and forwarding like every other class.

Disambiguation and forwarding¶

For each load, against every store:

older_store[st]      = stq[st].is_valid &&
                       (stq_committed[st] || stq_pos[st] < ld_older_cnt[ld]);
unresolved_store[st] = older_store[st] && !stq_addr_ready_comb[st];
alias_store[st]      = older_store[st] && addresses share a word &&
                       byte masks overlap;
alias_full_cover[st] = alias_store[st] && store mask covers the whole load;

The outcome is:

Condition

Result

an older store has no address and the load’s wait_older bit is set

stall (otherwise the load proceeds; see load speculation below)

youngest alias has no data yet

stall

youngest alias fully covers the load

forward from the store queue

youngest alias only partially covers

stall until the store drains

youngest alias is an atomic

stall until the atomic drains

For example, an older word store to address A can forward all four bytes to a younger word load from A. An older byte store covers only part of that word, so a younger word load must wait. ORCA does not merge bytes from the store queue with bytes from the cache.

The youngest alias is found by masking every alias candidate that has a younger alias, using store-queue position from the head pointer. This avoids a serial mux chain across the twelve stores on the D-cache request path.

An atomic sits in the store queue with its address and rs2, but rs2 is not the value it leaves in memory, so it never forwards. A younger load of the same word waits until the atomic leaves the queue. From then on the LSU is busy with the atomic until it finishes, so the load reads the new word. A load of another word can still forward from an older plain store across the atomic.

Loads speculate past unresolved older stores, guarded by a one-bit wait table and order-violation replay (next section). There is no store-set predictor.

Load speculation and order violations¶

A load does not wait for every older store address. It waits only if its wait_older bit is set. Otherwise it ignores older stores whose address is unknown, and it still obeys the resolved ones (forward, or stall on partial cover, missing data or an atomic). wait_older is set at insertion from a 256-entry, one-bit table indexed by pc[9:2]. The table is distributed RAM that starts at zero and has no reset.

The “an older store is unresolved” vector that wait_older loads check is registered, so it reaches selection one cycle late and the store-queue scan stays off the select-to-issue-packet path. The vector is only a performance hint. A load released by a stale value is still checked by violation detection and replayed if it was wrong. A new store reaches the register before any load allocated with it can have an address.

In the cycle after a store’s address arrives (stq_resolved_q), the queue compares that store, through the word-match bits taken when that address arrived (viol_same_q, one bit per load) and the byte masks, with every younger load that has already executed. LR writes nothing and is skipped. The oldest overlapping load is the violation. Its ROB ID goes to the ROB in a register (replay_valid, replay_tag), and in the next cycle its table bit is set. The ROB refetches from that load when it reaches the head (Commit). A slow sweep clears one entry every 512 cycles, so a full pass takes 2^17 cycles and a load that stopped colliding speculates again. A new violation wins over the sweep in the same cycle. The table is only a hint: a bit that is stale, aliased by another load, or left over across a reset can hold a load back for a while, and it can never make a load wrong.

A load that forwarded from a younger store may be flagged needlessly when an older aliasing store resolves. A refetch is always correct and only slower.

The report is not suppressed during branch recovery. The store’s resolution is a one-cycle pulse, so a violating load older than the mispredicted branch would otherwise retire its stale value. The oldest violator is reported unconditionally. If it is younger than the branch, it is killed with every younger violator, and the ROB ignores the replay for an invalid entry. lsq_entry_tb checks both recovery offsets.

Memory arbitration: two stages¶

select:
  oldest load candidate                    -> stage register holds the load
  otherwise a load whose address arrives   -> bypass straight into the stage
    from the AGU this cycle (cacheable,       register
    allowed by the wait table)
  otherwise authorized store-queue head    -> stage register holds the store
  (the store goes first instead when the store queue has two or fewer free slots)
issue (the cycle after):
  store -> dmem request; the store leaves the queue only on acceptance
  load  -> dmem request from the register; in parallel, its
           word-match bits (iss_same_q: taken as it entered the stage
           register, kept current while it waits there) are checked against
           older resolved stores:
             youngest alias covers the load -> forward, cancel the request
             alias cannot forward           -> cancel, bounce the load
             no alias                       -> the cache answers

Loads go first because a committed store is already architecturally done and only has to reach the cache eventually, while a load is usually on some instruction’s critical path. Pointer chasing shows the difference: in a loop that loads the next pointer and then stores to the node it came from, a store that went first would hold the cache for two cycles on every iteration, right when the next pointer load arrives. A store still goes first when the queue is nearly full, so stores always drain. The bypass load’s AGU result feeds this choice, which is the one place the selection does not come from registered state alone.

A load candidate has its address, has not executed, is not held by the wait table, and has not bounced since the store queue last changed (a store resolved or left). An uncached load is a candidate only at the ROB head with no authorized store pending, so it never needs forwarding or a cancel and never reads a device speculatively. dmem_cancel tells the LSU to drop the response of the request issued that cycle and not to wake its consumers.

Only the selected load is checked for forwarding, which makes that logic 1 by 16 instead of 16 by 16 and lets the cache request start at a register. Stores issue one cycle after selection, and back-to-back stores still go out every cycle, because the next entry is selected while the head leaves. An executed load keeps its slot until it retires, and a store’s slot frees when its request is accepted. Allocation readiness comes from registered validity, so freed capacity becomes visible on the following cycle.

Store authorization¶

Stores compute addresses and data speculatively but never become visible until the ROB authorizes them. commit_store_vals is that token. The queue maps tokens onto the first unauthorized valid entries in the occupied FIFO prefix. store_commit_mask counts each entry’s eligible predecessors independently of the token count, and then authorizes entries whose rank is less than that count. This keeps the late ROB token out of the rank accumulation. It matches a simple token-limited walk, including holes, circular wrap, 0, 1 or 2 tokens and a blocked authorized head. The precise protocol normally has one token in flight, and the helper does not assume that restriction. lsq_tb runs a case that compares the helper with the simple walk across 112,512 cases at depths 4 and 8, and it also compares the production wiring during queue traffic.

Atomics use the same token. The ROB issues it for an atomic only when the atomic is the head and its address has resolved, so the atomic drains like a committed store but is non-speculative and has no older store ahead of it. The queue sends it to the LSU as an OPC_AMO packet carrying the operation in funct7 and its destination register.

The token never reaches the memory request in its own cycle. The committed bits that the request logic reads are the registered ones, so an authorized store issues in the cycle after the ROB’s token. That removes the chain commit decision, authorization, LSQ request, router and cache write enable. lsq_tb checks that a token alone does not produce a store request in its own cycle.

The queue also registers the token itself, so the ROB’s commit decision never reaches the store queue in its own cycle. The store still retires in the cycle after authorization, and the queue marks it committed a cycle later. The token in flight counts as pending in stq_drained (so fence.i and an uncached load at the head still wait for it) and in flush preservation.

Flush and recovery¶

The LSQ treats two events differently, and the difference is what makes this block hard.

Flush (architectural) preserves committed stores. They are already architecturally visible and must still reach memory:

stq_committed <= stq_flush_keep;          // in-order committed prefix
stq_tail      <= stq_add(stq_head, stq_flush_count);
ldq[i].is_valid <= 1'b0;                  // every load dies

Branch recovery is a two-cycle sequence. On recovery.val the LSQ latches the branch’s age coordinate and sets recovery_pending_q. In the following cycle it does the actual cleanup:

recovery_head_q       <= rob_head_q;
recovery_branch_age_q <= recovery.rob_tag - rob_head_q;

Splitting it this way keeps the age comparison out of the cycle that resolves the branch. Throughout both cycles recovery_active blocks allocation and memory issue, which lets the cleanup logic read registered state directly and not the combinational next state.

Stores survive recovery if they are committed or older than the branch. Loads survive only if they are older.

Known limits¶

  • Load speculation uses only a one-bit wait table. There is no store-set predictor.

  • A store generates its address only when its data register is ready too, because there is no separate store-address and store-data issue.

  • Partial-overlap forwarding is not supported, and the load stalls instead.

  • One memory operation issues per cycle across both queues.

  • The store queue is a strict FIFO, so a blocked head blocks all draining.

Tests¶

sim/cpu/tb/5-issue/ holds these benches:

  • lsq_tb: forwarding, aliasing, ordering, flush preservation, the two-cycle recovery, first-result-wins and faulting AGU results.

  • lsq_entry_tb: entry contents, capture by tag, and forwarding of every access size at depths 4 and 8.

  • issue_tb: memory work reaches only the AGU, with base, immediate and store data, and advances while the multiply/divide and CSR units are busy.

  • register_read_tb, fast_wakeup_tb and spec_wakeup_tb: operand reads, fast wakeup and speculative load wakeup.

  • dispatch_tb: a memory op needs a scheduler lane and a queue slot.

Mutations that drop store-data capture, let a second result overwrite an entry, or route memory work to the CSR unit each fail a bench.
