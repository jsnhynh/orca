L1 caches¶

ORCA has private L1 instruction and data caches in the CPU clock domain. The instruction cache is rtl/cpu/cache/icache.sv. The data cache is rtl/cpu/cache/cache.sv, a parameterized set-associative cache. rtl/cpu/cache/cpu_l1_subsystem.sv wires them together with a small line-port arbiter, and a separate data router chooses between the D-cache and uncached AXI. Both caches are 16 KiB, two-way, with 64-byte lines.

Related notes: Core, Stage 1: Fetch, Memory and Machine-mode traps.

The instruction cache¶

icache.sv keeps each way’s data as one 64-bit word per RAM row ({set, word}), so a lookup reads one fetch group per way and never a whole 512-bit line through a wide line mux. Tags sit in a small RAM per way. The valid bits and the replacement bit sit in one more small RAM (meta_mem, one word per set). A RAM has no reset and no one-cycle clear, so reset and FENCE.I both clear it with a sweep that writes zero to one set per cycle (S_CLEAR). The cache accepts no request during the sweep, and the sweep after reset counts as quiescent because it has no memory traffic.

  • F1 (accept). The request address drives the tag and data RAM addresses and is registered. F2 reads the set’s valid bits from that registered index.

  • F2 (lookup). Tag compare and way select act straight on the RAM outputs. A hit is presented combinationally. A miss starts a refill and drops a request accepted in the same cycle, so the requester replays both.

  • Refill. Four 128-bit beats, with one outstanding. Each beat writes its low word on arrival and its high word in the next cycle, so the single RAM port needs no line buffer. The tag write, the valid set and the replacement update happen with the last word.

cpu_l1_subsystem.sv wraps the cache in a response adapter, so the core sees a registered response with backpressure. An output register (out_valid_q, out_data_q) takes the F2 hit when it is free, and the missed lookup and its dropped successor are replayed in order (replay_a_q, replay_b_q). That register lines the response up with the predictor’s metadata, which is captured one cycle after the request. The registered response also saves area and removes the FTQ-to-I-cache-SRAM path from the critical-path list. icache_tb checks hits, misses with a replayed successor, kill, hold, FENCE.I and refill sequencing.

The adapter register stays because removing it would answer a hit one cycle earlier, and the BTB/TAGE verdict would then have to come straight from the table RAM outputs in the same cycle as the I-cache tag compare and the fetch hold and push decision. I expect that path to be about as long as the clock period or longer [inference], which would cost back the frequency the change was meant to buy.

The data cache¶

cache.sv is the data cache:

Parameter

Value in the core

CACHE_SIZE

16 KiB

BLOCK_SIZE

64 B

ASSOCIATIVITY

2 (the only supported value)

DATA_WIDTH

32

It returns the lookup result without an extra response register, and it has the pending request slot described below.

L1 integration¶

cpu_l1_subsystem.sv instantiates the two caches. It also owns a four-entry FIFO of accepted I-cache request addresses. Cache responses carry data but not an address, so the FIFO head supplies the matching response PC to fetch, even though the cache pipeline can have more than one request outstanding. Simultaneous request and response handshakes shift the old head and add the new address without changing occupancy. A frontend kill or cache maintenance clears the FIFO, and a replacement request accepted on that same edge becomes its first entry.

The same wrapper blocks both core ports during FENCE.I, drains stale I-cache responses internally, and contains the maintenance state machine described below. It presents one line port to the rest of the SoC, so neither cache knows whether the memory behind it is the boot ROM, the board’s DDR or the simulation model of DDR.

Timing shape¶

cycle n:    accept request, drive SRAM index
cycle n+1:  compare tags, select way, produce hit response

Tags use orca_sram_1rw, and data uses the byte-masked orca_sram_1rw_xpm wrapper. Both provide one-cycle synchronous storage reads. Tag SRAM is one instance per way, and data SRAM is sixteen 32-bit instances per way.

Valid, dirty and precomputed replacement state of every set live in one small LUT RAM word (meta_mem), read like an array at the request set and at the maintenance set and written once a cycle (a hit, a refill completion, or a maintenance clear). Replacement needs one victim bit per set. A RAM has no reset, so after reset the cache sweeps every set to zero (C_INIT, one set per cycle) and accepts no request until it finishes; that sweep counts as quiescent because it has no memory traffic. A tag SRAM word uses only its low tag bits, and each 128-bit backing-memory beat spans four 32-bit data banks. Store-hit data repeats the CPU word across the line, and byte write enables select the affected bytes while the SRAM preserves the rest, so a store hit never reads, merges and writes the whole line. A store miss still merges its bytes into the completed refill, because that write enables every byte. Elaboration-time checks reject unsupported set, line, tag and bank geometries instead of silently truncating them.

With 16 KiB of capacity and two ways, there are 128 sets.

A pending slot holds one speculative successor request. Request readiness is therefore a registered capacity decision and does not depend on the current cycle’s hit result, which lets sequential hits sustain one request per cycle without putting the hit comparison on the request-accept path. If the successor was accepted just before the current lookup proves to be a miss, it stays in pending_* and replays after the refill. The cache uses resp_hold_* only when the core backpressures a hit or refill result, and valid stays high until the response handshake completes.

State machine¶

C_IDLE -> C_SRAM_READ -> hit?  -> response / next lookup
                      -> miss? -> C_WRITEBACK (if victim dirty)
                               -> C_REFILL -> C_REFILL_WRITE -> response / replay

C_MAINT_READ -> C_MAINT_CHECK -> C_MAINT_WRITEBACK (if dirty)
             -> next set/way or C_MAINT_DONE -> C_IDLE

Refills and writebacks move MEM_LINE_BITS (128 bits) per beat, so a 64-byte line is four beats. A refill allows one read request at a time: the cache sets refill_wait_resp_q after a beat request is accepted and does not request the next beat until its response returns. The completed line is written to the chosen way in C_REFILL_WRITE, and a write miss applies the original byte mask to that new line before responding.

One 512-bit register (line_q) and one tag register (wb_tag_q) serve three uses: the dirty victim being written back, a FENCE.I maintenance writeback, and the line being refilled. The three never overlap, because the states are exclusive, an evicted line is dead once its last beat is accepted, and the refill overwrites all four beats.

Replacement¶

Each set keeps a precomputed replacement way in its meta_mem word. Reset starts at way zero. A hit in a full set selects the other way as the next victim, and a hit in a partly filled set keeps the invalid victim. Every refill makes the other way the next victim. This is exact LRU with one bit per set, including the order in which invalid ways are filled. A completed maintenance walk resets the replacement order. The victim is read from the set’s word, so the miss path does not compute LRU comparisons.

Cache maintenance¶

FENCE.I drives a maint_req and maint_done handshake. The cache walks every set and way (C_MAINT_READ, C_MAINT_CHECK, C_MAINT_WRITEBACK), writes back dirty lines when maint_writeback is set, and invalidates as it goes. C_MAINT_DONE raises maint_done for one cycle and returns to C_IDLE.

cpu_l1_subsystem.sv sequences the two caches through a small state machine (FENCE_IDLE, FENCE_DCACHE, FENCE_ICACHE, and a one-cycle FENCE_DONE). The D-cache goes first with maint_writeback=1 and writes back and invalidates. The read-only I-cache goes next with maint_writeback=0 and invalidates. Both caches refuse ordinary CPU requests while maintenance is in flight. Request readiness stays low outside FENCE_IDLE: for the D-cache, both req_valid into the cache and req_ready back to the router are gated, and a simulation assertion checks that every handshake at the L1 boundary is also a handshake at the cache. Maintenance starts (maint_start) only once the pending successor (pending_valid_q) and any held response (resp_hold_valid_q) are both empty, and maint_req already stops new acceptance. See Stage 8, Commit for the ROB side of the handshake. The instruction cannot retire before fence_i_done fires.

The I-cache lookup reads its two valid bits in the compare cycle from the registered index. The valid bits change only during the clear sweep, when no request is accepted, and at refill completion, when none is accepted during the refill. A simulation shadow asserts that the registered read matches on every lookup.

Kill¶

The I-cache accepts a kill input driven by frontend redirects. It drops the current lookup (a killed miss starts no refill) and can accept a registered replacement PC in the same cycle. This guarantee is what lets fetch omit a response-side epoch filter: a kill consumes every stale response before a replacement request is accepted. The data cache has no kill.

Data-memory router¶

dmem_router.sv holds one LSU request at a time and saves its write flag, address, data and byte enables. Addresses in the uncached DMA region, or at or above the peripheral base, use AXI. Other addresses use the private D-cache. The exact ranges come from soc_pkg.sv and are listed on the Memory page.

R_IDLE
  +-- cacheable ----> R_MEM_REQ ------> R_MEM_RESP ------> R_IDLE
  +-- AXI read -----> R_AXI_READ_REQ -> R_AXI_READ_RESP -> R_IDLE
  +-- AXI write ----> R_AXI_WRITE_REQ -> R_AXI_WRITE_RESP -> R_IDLE

The cache request may be accepted in the original idle cycle, and otherwise R_MEM_REQ holds it until the cache is ready. AXI transfers are single-beat, 32-bit INCR transactions. AXI write address and write data are independent channels, so aw_done_q and w_done_q remember either handshake until both finish. Read and write response codes other than OKAY become core_resp_error, and the LSU turns that bit into a precise access fault. The cacheable path has no error input and always reports success.

The router holds a response until the LSU asserts core_resp_ready, then returns to idle. It preserves the request tag indirectly through the LSU’s one-outstanding-request state and does not add IDs to this local interface.

The cycle a cacheable response arrives counts as idle. core_req_ready is high in R_IDLE and in R_MEM_RESP while mem_resp_valid is high, so the next request is taken in the same cycle as the response and cacheable loads and stores can go back to back. Two rules keep that safe. The ready looks only at the state and at mem_resp_valid. It does not look at the new request, because the address is only driven when the request fires and that would close a loop through the load/store queue. It does not look at core_resp_ready either, so the LSU only presents a request beside a response when it has room to take that response (see LSU). A simulation assertion fires if a request is ever taken beside a response the core cannot accept. AXI requests still wait for idle.

Line-port arbitration¶

Both caches share one 128-bit backing-memory line port. cache_arbiter.sv picks between them with a fixed priority and remembers which cache owns the outstanding read until the data returns:

grant_ic = imem_req.valid;
grant_dc = !imem_req.valid && dmem_req.valid;

Instruction traffic always wins ties. A stalled fetch blocks the whole frontend, while a stalled load or store holds up only one backend queue entry. resp_src_q records which side issued the accepted read, so the single response channel can be routed back correctly. resp_pending_q qualifies the return, so a reset or an unsolicited response cannot be delivered to a cache. It does not gate the outgoing request in this module. The backing line-port contract supplies that serialization by deasserting mem_req_ready while its one read is pending, and accepting a second read early would overwrite the saved owner.

D-cache writebacks are not tracked by resp_src_q. The backing memory model has no response for writes, so only reads need return-routing state.

Known limits¶

  • There is one outstanding line fill, and a second miss waits.

  • There is one outstanding line read response, shared between both caches. The port can still accept response-free writeback beats one at a time.

  • There is no prefetcher and no non-blocking miss handling.

  • Cacheable RAM errors are not reported, and only the uncached/MMIO AXI path produces access faults. See Machine-mode traps.

  • I-cache priority can delay a D-cache refill or writeback when both request the line port together. There is no fairness rotation.

Tests¶

sim/cpu/tb/cpu_cache_tb.sv and sim/cpu/tb/cache_replacement_tb.sv cover hit and miss timing, a miss with a replayed successor, two-way replacement, dirty writeback and FENCE.I maintenance. sim/cpu/tb/cache_contract_tb.sv adds independent byte and LRU scoreboards, with every word offset and byte mask, held refill responses, memory backpressure, dirty eviction, reset and exact streaming hit throughput. fence_i_load_test runs loads straight after fence.i, and cache_contract_tb also checks maintenance with requests in flight.
