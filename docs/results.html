Results¶

This page reports measurements of a stable build on the Kria KV260 (xck26-sfvc784-2LV-c). Board numbers come from runs over JTAG, and timing and size numbers come from Vivado place-and-route reports.

Board Figures¶

  • CoreMark: 1,032 CoreMark/s at 200 MHz, 5.16 CoreMark/MHz. IPC is 1.51.

  • Embench-IoT: a speed score of 2.31 per MHz over all 19 benchmarks on the board (./orca board embench), 461 per second at 200 MHz, and 2.36 in simulation, where memory is faster. Both runs retire exactly the same instructions.

  • Architecture tests: all 67 pass on the board, and every test retires exactly the instructions the simulation retires.

  • Linux: kernel 6.18.7 without an MMU reaches /init after 1.53 s of kernel time (2.32 s on the earlier 150 MHz build) and provides a shell with 256 MiB of RAM.

Timing and Utilization¶

The full SoC closes timing at 5.0 ns (200 MHz) with no failing endpoints and no setup or hold slack to spare (0.000 ns). The same netlist lands between -0.56 ns and 0.000 ns depending on the placement settings, so I try several and publish the one that closes (see Reaching 200 MHz). The SoC has no on-chip RAM besides the L1 caches: all program and data memory is the board’s DDR.

Prediction and tests¶

  • Branch prediction: 98.9% conditional accuracy and 2.1 mispredictions per thousand instructions on the comparison CoreMark binary in simulation.

  • Architecture tests: 67 of 67 official RISC-V tests pass in simulation and on the KV260 board. One of them, InterruptsSm, raises interrupts through the timer’s memory-mapped registers and then idles a fixed number of loop iterations for each to arrive. That idle count is a platform setting, and it is set long enough for the board’s memory-mapped bus latency. See Verification.

Comparison with other cores¶

I compared ORCA with three open-source out-of-order RISC-V cores that I could build and run myself, NaxRiscv (SpinalHDL), RSD (SystemVerilog) and BOOM (Chisel), and with two Arm cores, the Cortex-A9 (application class) and the Cortex-R8 (real-time class). The open cores run the same CoreMark and Embench-IoT sources, built with the same compiler (GCC 15.2) and flags, each in its own simulator, and are implemented in the same Vivado flow as ORCA’s core. Arm’s cores cannot be downloaded and run that way, so their figures are Arm’s published ones and are marked with *.

Method¶

Each open core is implemented out of context on the KV260 part (xck26-sfvc784-2LV-c) with one clock, unconstrained ports, and the same Vivado directive profile. The scope is the core plus its L1 caches: ORCA’s cpu, NaxRiscv’s NaxRiscv, RSD’s Core and BOOM’s BoomTile. CoreMark runs 10 iterations from a cold start on every open core, so cache warm-up is included the same way for all of them.

All the open-core figures in this table come from simulation, at -O3 with GCC 15.2. ORCA’s column is the RTL of the 200 MHz board build, and its area comes from routing that RTL out of context at 5.0 ns. On the board the same build scores 5.16 CoreMark/MHz; the board run does 12,000 iterations, while the comparison runs 10 from a cold start. The per-second row multiplies the simulated CoreMark per MHz by the clock each core reached, so it is a projection for every core, ORCA included; ORCA’s measured figure on the board is 1,032. NaxRiscv’s own published figure of 5.02 comes from its own CoreMark build. Each core runs in its own testbench with its own memory model, which is the largest difference left between the runs.

Embench-IoT gives a wider view than CoreMark. All the open cores run the same 19 benchmarks, and the score is Embench’s speed score scaled to 1 MHz. ORCA is ahead of NaxRiscv on nsichneu (NaxRiscv takes 97% more cycles), matmult-int (12%), aha-mont64 (8%), ud (7%), sglib-combined (7%) and tarfind (6%), and behind on statemate (NaxRiscv takes 11% fewer cycles), huffbench (7%), depthconv (5%) and xgboost (4%). ORCA is ahead of RSD on all 19. BOOM scores 2.17, but its 64-bit code changes the work on some programs: aha-mont64 needs 57% fewer instructions on RV64, and BOOM takes half of ORCA’s cycles there. Without that one program BOOM scores 2.14 and ORCA 2.43. BOOM takes fewer cycles than ORCA on 6 of the 19, and the most more on ud (2.7 times ORCA’s cycles) and nsichneu (2.2 times).

Area & Speed. ORCA uses about 2.5 times the LUTs of NaxRiscv and 1.9 times those of RSD for the same scope. BOOM does not fit on the KV260 at all: it needs 123.2k LUTs after synthesis and the part has 117.1k, so Vivado stops before placement and BOOM has no clock in this flow. Its floating-point unit and the logic around it account for about 28k of those LUTs, and its 64-bit datapath doubles the width of everything else: its 80-entry integer register file alone is 10.3k LUTs. The largest ORCA blocks are in the chart above: the issue stage (the load and store queues and the scheduler), execute and the branch predictor. ORCA keeps full checkpoints per FTQ entry, a 64-bit global history with four 1,024-entry TAGE tables, a 512-entry L0 table, and a 64-entry register file with six read ports. ORCA and NaxRiscv both reach 200 MHz in this flow, but ORCA’s critical paths are 62 to 75% routing delay through these larger structures, so it needs a placement search to get there.

How ORCA compares, in charts¶

How the structures were sized¶

Each structure size was picked against cycles and area, and these panels show what the other sizes would cost or save on the RTL of late October, before the 200 MHz work. The decisions page has the later measurements, including what the larger sizes cost in clock. The scheduler and the load and store queues matter most: eight scheduler entries cost 4% on CoreMark and 11% on picojpeg, and eight queue entries cost 10% on statemate. TAGE keeps paying as it grows: 2,048 entries per table would save 1.5% on the Embench subset, most of it on huffbench. A shorter history helps Embench but costs CoreMark 1.8%. An 8-entry FTQ costs 2.6% on CoreMark and 5% on wikisort. Some structures are larger than these programs need: the return stack performs the same from 4 to 32 entries, the BTB stops helping at 256 entries, and a 128-entry ROB runs in exactly the same cycles as 64: at 64 entries the ROB is never what stops dispatch in these programs. Where a larger size buys a percent or two, I kept the smaller one for area and timing.
