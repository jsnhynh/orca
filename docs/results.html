Results¶

This page reports measurements of a stable build on the Kria KV260 (xck26-sfvc784-2LV-c). Board numbers come from runs over JTAG, and timing and size numbers come from Vivado place-and-route reports.

Board Figures¶

  • CoreMark: 4.54 CoreMark/MHz and 681 CoreMark/s at 150 MHz. IPC is 1.36.

  • Linux: kernel 6.18.7 without an MMU reaches /init after 2.44 s of kernel time and provides a shell with 256 MiB of RAM.

  • Embench-IoT: a speed score of 1.74 per MHz over all 19 benchmarks on the board (./orca board embench), and 1.81 in simulation, where memory is faster. Both runs retire exactly the same instructions.

Timing and Utilization¶

The full SoC (no FIN) closes timing at 6.667 ns (150 MHz) with +0.002 ns of worst setup slack and no failing endpoints. 150 MHz is at the edge: the same RTL misses by up to 0.2 ns with some Vivado directive sets, and the published build uses the one that closed. It has no on-chip RAM besides the L1 caches: all program and data memory is the board’s DDR.

Prediction and tests¶

  • Branch prediction: 99.0% conditional accuracy and 2.2 mispredictions per thousand instructions on the board’s CoreMark binary, measured over 20 iterations in simulation.

  • FIN DMA through DDR (simulation): FIN’s DMA reads take about 59 cycles per burst, up from 46, so FIN jobs run about 13% longer on the same data (the convolution benchmark’s job time goes from 33,494 to 37,745 cycles). DMA writes are unchanged at about 105 cycles per burst. The simulated DDR is ideal, real DDR latency was not measured, and FIN has not been brought up on an FPGA.

  • Architecture tests: 67 of 67 official RISC-V tests pass in simulation and on the KV260 board. One of them, InterruptsSm, checks the exact instruction each interrupt lands on against the reference model, so on the board it passes when run on its own and can fail when it runs straight after the others: a cache miss in front of the expected instruction lets a pending interrupt arrive one instruction early, which the architecture allows. See Verification.

Comparison with NaxRiscv and RSD¶

I compared ORCA with the two open-source two-wide out-of-order RV32 cores closest to it in scope: NaxRiscv (SpinalHDL) and RSD (SystemVerilog). All three run the same CoreMark source, flags and compiler. ORCA’s numbers come from a Kria KV260 board and from simulation. NaxRiscv and RSD were run in their own Verilator testbenches and implemented in the same Vivado flow as ORCA’s core.

Method¶

Each core is implemented out of context on the KV260 part (xck26-sfvc784-2LV-c) with one clock, unconstrained ports, and the same Vivado directive profile. The scope is the core plus its L1 caches: ORCA’s cpu, NaxRiscv’s NaxRiscv, and RSD’s Core.

ORCA’s CoreMark per MHz is a board measurement, over 7,000 iterations; the other two are 10-iteration simulations, which include their cold cache misses, so ORCA’s small lead per clock is within that difference. NaxRiscv and RSD figures come from their simulators running the same binary; their per-second figures multiply the simulated CoreMark per MHz by the clock each core reached in the implementation runs, so they are projections. NaxRiscv’s own published figure of 5.02 CoreMark per MHz comes from its own CoreMark build; with the common compiler and flags it measures 4.47.

Embench-IoT gives a wider view than CoreMark. All three cores run the same 19 benchmarks, built with the same compiler and flags, in their own testbenches, and the score is Embench’s speed score scaled to 1 MHz. ORCA is level with or ahead of NaxRiscv on the arithmetic kernels (aha-mont64, edn, matmult-int) and behind on control-heavy and divide-heavy code: ud divides in its inner loop, and ORCA’s divider produces one quotient bit per cycle. ORCA is ahead of RSD on 16 of the 19.

Area & Speed. ORCA uses about 2.8 times the LUTs of NaxRiscv and 2.1 times those of RSD for the same scope. The largest ORCA blocks are the execute stage (5.8k LUTs), the branch predictor (5.4k, of which the FTQ is 1.9k and TAGE 1.4k), the load/store queues (4.1k), the ROB (4.0k), the D-cache (3.6k), rename (2.6k), the scheduler (2.4k), the payload array (1.6k), and fetch (1.4k). ORCA keeps full checkpoints per FTQ entry, a 64-bit global history with four 1,024-entry TAGE tables, and a 64-entry register file with six read ports. More work needs to be done here to identify the utilization gap. This is likely the reason for the frequency gap as well, since the critical paths are dominated by routing delay.
